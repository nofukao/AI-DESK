# AI-DESK 1.0.0 の設計 — なぜこの構造なのか

作成: 2026-09-14

この文書は、**将来の自分と、後から加わるメンバーのため**のものです。
「なぜこうなっているのか」が分からないと、良かれと思って壊してしまうためです。

**採用しなかった案も書いてあります。** そちらのほうが価値があることが多いからです。

---

## 1. インスタンスを git のクローンにしなかった

**インスタンスは、配布物フォルダの「コピー」です。`.git` は存在しません。**

クローンにすれば更新は `git pull` だけで済み、版ずれも起きません。**それでも採りませんでした。**

理由は1つです。**インスタンスの中には業務の機密情報が入ります。**
そこに `.git` があると、誰かが `git add .` と `git push` をした瞬間に外部へ出ます。
**push は実質的に取り消せません。** 履歴を書き換えても、既にクローンされていれば手遅れです。

事故の確率は低いかもしれません。しかし**起きたときの損害が回復不能**です。
更新の手間（`update-instance.ps1` を叩く）は、その保険料として安いと判断しました。

この判断は、配布物の `CLAUDE.md`「絶対遵守ルール2: Git の不使用」として利用者にも伝えています。
**理由まで書いてあります。** 理由の分からない禁止は、いつか誰かに破られるからです。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| インスタンスも clone にする | 上記。**この1点で却下** |
| clone にしたうえで `.gitignore` で業務データを除外 | 除外の設定を間違えた瞬間に出ます。**間違えたことに気づけない**のが致命的 |
| インスタンスをシンボリックリンク／ジャンクションで共有 | 1か所直すと全員に即座に効く反面、**壊したときも全員に効きます。** 段階的な更新ができません |

## 2. 配布物フォルダを `AI-DESK\` と名付けた

開発リポジトリの中に `AI-DESK\` があり、その中身は**完成品のインスタンスとまったく同じ形**です。
そのままコピーすれば動きます。「配布物 = インスタンスのひな形」を、形で示しています。

**副作用があります。見た目が完成品なので、開発中にうっかりそこで実際の仕事をしてしまいます。**

対策を2つ重ねました。

1. **`.gitignore` のホワイトリスト方式**（→ 7）。後から増えたものは追跡されません
2. **開発用 `CLAUDE.md` に明記**。「`AI-DESK\` の中で実際の業務を行わない」

### 採らなかった案

`dist\` や `template\` という名前にする案がありました。取り違えは起きにくくなります。
しかし**コピーしたあとのフォルダ名が変わってしまう**か、リネームの手順が1つ増えます。
「コピーすればそのまま動く」という分かりやすさを優先しました。

## 3. `CLAUDE.md` と `PROFILE.md` を分けた

旧構成では、規則も業務知識も 1 つの `CLAUDE.md`（約28KB）に入っていました。
これを2つに割りました。

| ファイル | 中身 | 配布 | 現場で直せるか |
|---|---|---|---|
| `CLAUDE.md` | どの組織でも通用する規則 | する | **直さない**（コピーなので消える） |
| `PROFILE.md` | その組織の前提知識（業態・用語・資料の場所） | しない | **自由** |

**理由は2つあります。**

1. **可搬性。** 業務知識が混ざったままでは、他の組織・他の部署にコピーできません
2. **リポジトリを Public にできる。** 実在の会社名・取引先名・物件名が配布物から消えました。
   この分離が済むまでは Public 化を検討できません

読み込みは `CLAUDE.md` の冒頭に置いた `@PROFILE.md` の 1 行で行われます。
`PROFILE.md` が無くても規則はすべて有効で、**「前提知識が無いから作業しない」とはさせません。**

1.0.0 では同じ考えで、**読み取り範囲を `.claude\settings.local.json`** に分けていました。
**1.1.0 で、読み取り範囲の設定そのものをやめました**（→ 14）。

## 4. インスタンスの識別を、フォルダ名ではなく `.ai-desk\VERSION` にした

**`.ai-desk\VERSION` があるフォルダが、インスタンスのルートです。**
フォルダ名は `AI-DESK` でも `AI-DESK1` でも `営業部AI-DESK` でもかまいません。

**理由は、名前を自由にし、何個でも置けるようにするためです。**

- 通常業務用と実験用を分けたい
- 部署ごとに置きたい
- NAS が使えないときだけローカルで作業したい

フォルダ名で判定すると、この全部ができなくなります。
また、**名前の規則は必ず破られます**（「AI-DESK_旧」「AI-DESK - コピー」）。
**ファイルの有無なら、破りようがありません。**

この判断は規則の根幹なので、`CLAUDE.md` の「【最重要】書く場所を間違えないために」の中で
定義してあります。

---

## 5. 規則の判定条件に、パス区切り文字を使わない

「パス文字列に `\out\` が含まれるか」ではなく、
「**そのタスクフォルダの `out` の中か**」と**構造**で書いています。

**これは移植のための配慮ではありません。いま効く堅牢性です。**

- 文字列判定では、**ルート直下の `out` も、別のタスクの `out` も通ってしまいます**
- 同じフォルダが、道具によって次のように見えます。**すべて Windows 上の話です**

```
PowerShell から:   Z:\AI-DESK\202610_見積比較\out
Git Bash から:     /z/AI-DESK/202610_見積比較/out
WSL から:          /mnt/z/AI-DESK/202610_見積比較/out
```

**本文の説明や例で `out\` と書くのは構いません**（読みやすさのため）。
直したのは「AI がこう判定せよ」と書いてある箇所だけです。

## 6. `Edit(*/out/**)` を変えずに済んだ

旧構成と新構成では、**カレントディレクトリから `out` までの深さが同じ**です。

```
旧: <個人フォルダ>\<タスク名>\out\     ← カレント = 個人フォルダ
新: <インスタンス>\<タスク名>\out\     ← カレント = インスタンスのルート
```

`.claude\settings.json` の `Edit(*/out/**)` は「カレントの1階層下の `out`」を意味します。
（1.0.0 では `Write(*/out/**)` も併記していましたが、**`Write(...)` のパス指定は一度も参照されていませんでした。** → 10）
**個人名の階層が消えたのに深さが変わらないため、権限設定に一切手を入れていません。**

これは偶然ではなく、**そうなるように新構成を決めました。**
権限設定は動作確認が難しく、間違えたときに気づきにくい部分です。触らずに済むなら、それが最善です。

なお `settings.json` のパターンは `Edit(*/out/**)` と `/` 区切りで書きます。
**この記法は全 OS 共通**で、元から中立でした。

## 7. `.gitignore` をホワイトリスト方式にした

```gitignore
/AI-DESK/**
!/AI-DESK/CLAUDE.md
!/AI-DESK/.claude/skills/**
    …
```

`AI-DESK\` の中をいったん全部無視し、**既知の配布物だけを `!` で戻しています。**

**理由**: `AI-DESK\` は見た目が完成品のインスタンスなので、
**開発中にうっかり実際のタスクフォルダを作ってしまう**ことが十分あり得ます。
ブラックリスト方式（`*.xlsx` を無視する等）では、想定していない形のものが漏れます。

**この方式の代償**: 配布物にファイルを足したら、`.gitignore` にも `!` 行を足す必要があります。
足し忘れると**追跡されません（＝ push されない）。安全側に倒れます。**
実際、フェーズ1で `settings.local.json.example` の `!` 行が漏れており、
`git check-ignore` で検出して足しました。**代償が想定どおりに働いた**形です。

## 8. 版ずれ問題と、配布原本による解き方

**新構成の最大の弱点です。**

旧構成の強みは「ルールの実体が1つしかない」ことでした。1か所直せば全員に効きます。
新構成では**インスタンスの数だけ `CLAUDE.md` のコピーが増え、必ず版がずれます。**
これは避けられません。**避けられないので、「ずれを見つけられる」ようにしました。**

```
<社内の配布原本>\AI-DESK\        ← 社内で1か所。publish.ps1 が置く
        .ai-desk\VERSION         ← 1.2.0

<任意の場所>\AI-DESK\            ← インスタンス
        .ai-desk\VERSION         ← 1.0.0
        .ai-desk\source.txt      ← 配布原本のパスが書いてある
```

1. `.ai-desk\VERSION` に版番号を持つ
2. `.ai-desk\source.txt` に**どこから来たか**を記録する（`new-instance.ps1` が書く）
3. **`疎通確認` が、配布元の版と自分の版を比べて知らせる** ← **これが一番効きます**
4. `update-instance.ps1` は、上書き前に差分を表示する
5. 現場での `CLAUDE.md` 直接編集は禁止。改訂案を `out\` に出して管理者に渡す導線がある

**「ルールの実体は1つ」という強みを、配布原本という形で取り戻しました。**
インスタンスは増えても、**原本は1つ**です。

配布元に届かない場合（NAS に繋がっていない、原本が移動した）は、
**失敗ではなく「確認できませんでした」と報告させます。** 嘘をつかせないためです。

### スキルは、利用者が自由に育ててよい

旧構成では、共通スキルを1か所に置けば全員に効きました。**新構成ではこれが失われます。**

**失われてよい**と判断しました。本システムは開発途上であり、
現状の仕様で利用者を縛るほうが、有用性を損なうリスクが大きいためです。
利用者は自分のインスタンスでスキルを追加・改造できます（AI がやる場合は承諾が要ります）。

代わりに2つ決めました。

- **配布物のスキル（`初期設定`・`疎通確認`・`継続タスク`）を直接書き換えると、次の更新で消える**（`CLAUDE.md` に明記）
- **利用者が足したスキルは、更新で触らない**（`update-instance.ps1` の仕様）

## 9. 配布物の一覧を、別に持たない

`new-instance.ps1` / `update-instance.ps1` / `publish.ps1` の3本は、
**「配布物フォルダの中に実在するファイル」を走査**します。マニフェストを別に持ちません。

**理由**: 一覧を二重に持つと、必ずずれます。
この作りなら「**配布物に無いものは触らない**」が、仕様ではなく**構造として**成り立ちます。
タスクフォルダも `PROFILE.md` も `settings.local.json` も、走査結果に現れないので触られません。

代償は、**開発リポジトリの `AI-DESK\` にゴミを置くと配布されてしまう**ことです。
`.gitignore`（→ 7）と、`publish.ps1` の確認表示で受け止めています。

## 10. 歯止めを「確認プロンプト」から「deny」へ移した（1.1.0）

> **この節の「例外3つ」と「読み取り範囲と `deny` の対」は、1.1.0 の公開前に取りやめ、
> hook に置き換えました（→ 14）。** 判断の経緯として残します。

**受け入れテストで穴が見つかりました。** 権限モードが「Auto」のとき、
ルート直下の `out\` への書き込みが**確認なしで通りました。**

`settings.json` の `disableBypassPermissionsMode: "disable"` が塞ぐのは
bypassPermissions だけで、**「自動」は塞いでいませんでした。**

### 何が問題だったか

歯止めを **`allow` と確認プロンプト**に置いていたことです。これは
**「利用者がモードを切り替えない」という前提**の上に立っていました。
その前提は、利用者の手元で簡単に崩れます。しかも**崩れたことに誰も気づきません。**

### どう直したか

**`deny` は権限モードに関係なく効きます。** そこで歯止めを `deny` に移し、
**そのうえで既定を「自動」にしました。**

| | 1.0.0 | 1.1.0 |
|---|---|---|
| 既定のモード | 確認あり（`default`） | **Auto**（契約の既定に任せる。設定ファイルでは指定しない） |
| 何が守っていたか | `allow` ＋ 確認プロンプト | **`deny`** |
| モードを変えられたら | **歯止めが消える** | **変わらない** |
| 作業の手間 | 毎回確認が出る | **止まらない** |

「確認を出して止める」のをやめ、「そもそも書けなくする」に変えたので、
**安全性を上げながら、同時に手間を減らせました。** 両立しないと思っていた2つです。

規則は「**配布物（更新で上書きされるもの）には書けない**」の1本にまとめました。
例外は `PROFILE.md`（自由）、`.claude\skills\`（承諾を得て）、
`settings.local.json` の `additionalDirectories`（同上）の3つです。
**育てる場所と、揃えておく場所を、`deny` の有無で表現しています。**

### 読み取り範囲と書き込み禁止を、対にした

> **読んでよい場所は、書いてはいけない場所でもある。**

`settings.local.json` には、読める場所（`additionalDirectories`）と、
そこへの書き込み禁止（`Edit` の `deny`）を**対で**書きます。
分けて考えさせないので、片方だけ足して片方を忘れる、が起きにくくなります。

これで、**Auto モードでも、AI が直接行う書き込みは資料フォルダに届きません。**
過去に実際に起きた事故（成果物を資料フォルダに直接出力した）は、**AI が直接書いた場合に限り**、機械的に塞がりました。
スクリプト経由の書き込みは塞がりません（→ 下の「それでも残る穴」）。

### 残る穴 — 正直に書いておきます

| 穴 | なぜ塞げないか |
|---|---|
| **インスタンスの外への書き込み**（デスクトップなど） | 事前に列挙できないためです。「自動」では確認なしで通ります。**ここは規則だけが頼り**です |
| **`deny` を書いたファイル自身を、AI が編集できる** | `settings.local.json` は AI が `additionalDirectories` を足せる必要があります。同じファイルの中に `deny` があるため、原理的には外せます |

2つ目は、**予防ではなく発見で受け止めています。** `疎通確認` が毎回
「読める場所すべてに、対になる `deny` があるか」を検査し、崩れていれば異常として報告します。

3つ目の穴（`.claude\settings.json` 側の `deny`）は、そのファイル自体を `deny` しているため、
**AI からは外せません。** 守りの中心はこちらに置いてあります。

### 1.1.0 の最初の実装にあった誤り（公式ドキュメントとの照合で判明）

実機テストの途中で Claude Code の公式ドキュメントと照合したところ、**設定の書き方に4つの誤り**がありました。
いずれも**エラーにならず、黙って効かない**種類の誤りです。

| # | 誤り | 実際の挙動 | 直し方 |
|---|---|---|---|
| 1 | `"defaultMode": "acceptEdits"` で Auto を既定にしたつもりだった | `acceptEdits` は画面の「Edit automatically」で、**Auto とは別のモード**。しかも `auto` は**プロジェクトの設定ファイルからは指定できず**、VS Code 拡張は**プロジェクトの設定を開始モードに使わない** | `defaultMode` を**書かない**。Pro・Max・Team 契約では、指定しなければ Auto で始まる |
| 2 | `Edit(./out/**)` でルート直下の `out` を塞いだつもりだった | `./out/**` は `out/**` と同じ扱いで、**deny では深さを問わず当たる。すべてのタスクの `out` が塞がれ、何も出力できなくなる** | 先頭を `/` にする（`Edit(/out/**)`）。プロジェクト設定では、起動したフォルダの直下だけに当たる |
| 3 | `Write(...)` と `Edit(...)` を対で書いていた | ファイルの権限は **`Edit(...)` だけで判定され、`Write(...)` のパス指定は参照されない**（起動時に警告が出る） | `Edit(...)` だけにする。`Edit` の deny は Write ツールの書き込みも止める |
| 4 | 資料フォルダを `Edit(Z:/**)` で塞いだつもりだった | Windows のパスは照合前に `/z/...` に直される。`Z:/**` は**起動フォルダからの相対パス**と解釈され、**Z: には一切当たらない** | `Edit(//z/**)` と書く（`//` がドライブの根、ドライブ文字は小文字） |

**2 は、実機テストで 8-1 を行えば「何も出力できない」として表に出たはずの誤りです。**
**4 は、テストでは表に出にくい誤りです。** 資料フォルダに書こうとしない限り、効いていないことに気づけません。
**設定の書き方は、実機テストだけでなく、ドキュメントとの照合でも確かめる**必要があります。

### それでも残る穴（ドキュメントで確認した事実）

- **Python などのスクリプトが自分で開くファイルには、`deny` は効きません。** `Edit` の deny が見張るのは、
  Claude Code 自身のファイル操作と、Bash が名前を挙げて扱うファイル（`cat` やリダイレクト先など）だけです。
  抽出スクリプトの書き出し先は、**規則（`CLAUDE.md`）と、Auto モードの安全チェックが頼り**です。
  OS のレベルで塞ぐサンドボックス機能は、ドキュメント上 macOS・Linux・WSL2 向けです
- **`.claude\` の中は Claude Code の保護パスです。** Auto モードでも書き込みは安全チェックに回されます。
  `初期設定` が `settings.local.json` やスキルを書くとき、確認が出ることがあります。
  歯止めとしてはむしろ好都合です（AI が自分の deny を黙って外しにくい）

## 11. `PROFILE.md` を、最初から置かないことにした（1.1.0）

1.0.0 の `new-instance.ps1` は、`PROFILE.example.md` を `PROFILE.md` にコピーしていました。
**これは間違いでした。**

`CLAUDE.md` の `@PROFILE.md` は、それを**毎回自動で読み込みます。** つまり作りたての
インスタンスでは、AI が**架空の会社（サンプル商事・事務機器の卸売）を、この組織の事実として
読み込んでいました。** `疎通確認` も「`PROFILE.md` はある → 正常」と報告していました。

**空である以上に悪い状態です。** 空なら「分からないので聞く」ですが、
これは「知っているつもりで間違える」です。

### どう直したか

**作らないことにしました。** 無ければ `@PROFILE.md` は何も読み込みません。

「マーカーを置いて、中身は無視しろと AI に指示する」方式も検討しましたが、採りませんでした。
**読んでから忘れろ、は読まないより弱い**ためです。

代わりに `初期設定` スキルを追加し、**対話で聞き取って作る**ようにしました。
手で書きたい人のために `PROFILE.example.md` は配り続け、
**手でコピーした人が中身を書き換え忘れた場合**に備えて、記入例には判別用の1行
（`AI-DESK-PROFILE-EXAMPLE`）を入れてあります。保険は残しつつ、主たる経路を変えた形です。

`settings.local.json` も同じ理由で作らないことにしました（その後、読み取り範囲の設定そのものをやめました → 14）。

### 「要らない」と言えること

前提知識を登録しない運用も選べます。その場合は `AI-DESK-PROFILE-NONE` を含む
`PROFILE.md` を書き、**以後は申し出ません。**
「いまはいい」（次回また聞く）と「要らない」（もう聞かない）を区別しています。
**一度断られたことを何度も聞くのは、それ自体が害**だからです。

## 12. マルチプラットフォーム対応は、当面やらない

### 決定

**AI-DESK は Windows 専用とします。** macOS / Linux 対応は行いません。

### 理由

1. **実際の利用がほぼ Windows**です
2. **動作確認のできない `.sh` を配るのは、無いよりかえって危険**です。
   「用意してある」と思って使われ、壊れていたときに誰も直せません

### それでも守った4点

「やらない」と「やれなくする」は違います。**いずれも追加コストがほぼゼロで、
後から施すと大仕事になるもの**だけを守りました。

| # | 守ったこと | なぜ今か |
|---|---|---|
| 1 | OS 依存の記述を `CLAUDE.md` の「実行環境について（Windows）」1章に集約 | 28KB の文書に後から施すのは大仕事。**分割のついでなら無料** |
| 2 | 規則の判定条件にパス区切り文字を使わない（→ 5） | **移植と無関係に、いま効く堅牢性** |
| 3 | `.gitattributes` に `*.sh text eol=lf` | 1行。将来 `.sh` を足したとき CRLF 混入で即死するのを防ぐ |
| 4 | `.ps1` でパスを文字列連結せず `Join-Path` を使う | 書き始めれば無料。PowerShell 7 は mac/Linux でも動くので、**移植の目が残る** |

### 今回の分割の副産物として、大半はすでに中立になっている

| 項目 | 状態 |
|---|---|
| ドライブレター | **解決済み** — 配布物に書かない。`PROFILE.md` と `TASK.md` に書く（サイト固有） |
| 業務フォルダのパス | **解決済み** — `PROFILE.md` へ |
| `settings.json` のパターン記法 | **元から中立** — `Edit(*/out/**)` と、全 OS で `/` 表記 |
| Office/PDF 抽出（openpyxl, pandas, pdfplumber…） | **元から中立** |
| タスクフォルダ方式・命名規則・作業記録 | **元から中立** |
| PowerShell スクリプト5本（hook を含む） | **残る依存その1** |
| `py` / cp932 / `.ps1` の BOM / 260文字制限 | **残る依存その2**（1章に集約済み） |

### 再開するときの手順

1. スクリプト3本と hook（`guard-write.ps1`）の `.sh` 版を書く（`setup_python.ps1` は winget 依存なので別途）
2. `CLAUDE.md` の「実行環境について（Windows）」に、macOS の節を足す
3. `py` → `python3` の分岐を入れる

**上の4点を守ってあれば、おおよそ1日**です。守っていなければ `CLAUDE.md` 全体の書き直しになります。

## 14. 読み取り範囲の設定をやめ、書き込み先を hook で限った（1.1.0）

**10 で作った「読み取り範囲と `deny` の対」を、公開前に取りやめました。**

### きっかけ

実機で `初期設定` を試したところ、読み取り範囲（`settings.local.json`）を最初に決めさせる流れに、
次の疑問が出ました。

- 読む場所は、**依頼（タスク）ごとに違う。** 最初に一度決めるより、`task.md` で指定するほうが自然
- **AI が読める範囲は、使っている人が読める範囲と同じ。** 設定を誤っても、AI が人以上の権限を持つことはない
- **本当に限りたいのは「書く場所」**で、それは「タスクフォルダ（特に `out`）だけ」と言い切れる

### deny では「ここだけ」と書けない

Claude Code の公式ドキュメントに、次のとおりあります。

> a deny rule can't carry allowlist exceptions

`deny` は「ここは禁止」を**並べる**方式で、「ここ以外は全部禁止」とは書けません。
だから 10 では、読める場所ごとにドライブの `deny` を対で書かせる必要があり、
**列挙できないデスクトップなどへの書き込みは、穴として残っていました。**

### hook なら「ここだけ」と書ける

`PreToolUse` の hook は、AI がファイルを書く直前に、決まったスクリプトを走らせる仕組みです。

> A hook that exits with code 2 stops the tool call before permission rules are evaluated

権限ルールより前に止めるので、**Auto を含むどのモードでも効きます。**
`.claude\hooks\guard-write.ps1` が書き込み先を調べ、次の3つ以外を止めます。

| 書いてよい場所 | 理由 |
|---|---|
| `<ルート>\<タスクフォルダ>\out\` の中 | 成果物の置き場所。AI-DESK の約束そのもの |
| `<ルート>\PROFILE.md` | `初期設定` と「PROFILE に足して」のため |
| `<ルート>\.claude\skills\` の中 | スキルを育てる自由度のため（→ 8） |

- タスクフォルダは「ルート直下のフォルダ。ただし `.` で始まるもの・`bin`・`00_タスクテンプレート`（旧 `task_template`）・`out`（`out2` なども）を除く」
- **`out` だけ**にしました（のちに `out2` など、数字を付けたものも → 16）。`TASK.md` は人が書いた依頼なので、AI には書き換えさせません
- 判定は文字列の見た目でなく、**絶対パスに直してから構造で**行います（→ 5）。
  `/c/...` の形、`/` 区切り、相対パス、`..`、大文字小文字の違いを吸収します
- 途中にジャンクション・シンボリックリンクがあれば止めます（見た目は `out` の中でも、実体が資料フォルダになりうるため）
- **判定できない形のパスや、スクリプト内のエラーは、止める側に倒します**
- インスタンスのルートは、スクリプトの2つ上のフォルダ（`.ai-desk\VERSION` があること）で決めます。
  起動したフォルダの名前には頼りません（→ 4）

### 読む側は、設定しない

- Auto モードでは、AI-DESK の外も確認なしで読めます（最初の1回だけ「読み続けてよいか」の確認が出ます）
- 読む場所は `TASK.md` の「見る場所」に従わせます（書かれていない場所は見ない。→ 16）
- 読ませたくない場所は、`PROFILE.md` の「**AI に読ませない場所**」（任意）に書きます。
  **読むことは、中身を AI のサービスへ送ることでもある**ためです。これは規則であって、機械的な禁止ではありません
- 副次効果: `additionalDirectories` を使わなくなったので、Z: が「作業フォルダ扱い」でなくなり、
  Z: への編集が自動承認の対象から外れました

### 付随して決めたこと

| 決めたこと | 理由 |
|---|---|
| `autoMemoryEnabled: false` | 自動メモリは `%USERPROFILE%\.claude\projects\...\memory\` に書きます。**`out` の外への書き込み**なので hook に止められ、失敗を繰り返すだけになります。組織の知識の置き場所は `PROFILE.md` です |
| `disableAllHooks: false` を明記 | ユーザー設定で hook を全部止めていても、プロジェクト設定の `false` が優先されるため |
| `deny` に `settings.local.json` と `hooks\` を追加 | hook が動かなかったときの2枚目の壁。`settings.local.json` に `disableAllHooks: true` を書かれると hook が止まるため |
| `settings.local.json.example` を配布物から外した | 読み取り範囲の設定が要らなくなったため |

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| タスクごとに `settings.local.json` を書き換える | Auto モードでは、読むのに設定が要らない。AI が自分の権限設定を毎回書き換えるのは、歯止めの意味を弱める |
| `dontAsk` モード（許可したもの以外すべて拒否） | Python の実行やシェルのコマンドまで1つずつ許可が要り、作業にならない。モードの切り替えにも出てこず、起動時の指定が要る |
| サンドボックス（プログラムの書き込みまで OS で縛る） | 公式ドキュメント上、macOS・Linux・WSL2 のみ。**Windows ネイティブは非対応** |
| シェルのコマンド文字列を hook で検査する | 変数や Python の中の書き出し先は見えない。**止めているつもりになる**ほうが危ない |
| 共有フォルダを読み取り専用にした別の Windows アカウントで AI を動かす | **プログラムの書き込みまで塞げる唯一の方法。** ただし情報システム側の作業になるため、今は採らない |

### 残る穴 — 正直に書いておきます

| 穴 | 手当て |
|---|---|
| **PowerShell が起動できない・時間切れ**のとき、書き込みは止まらない（Claude Code の仕様） | `deny`（ルートの `out`・配布物・設定ファイル）を2枚目の壁として残した。`疎通確認` 8-4 で、hook が実際に止めるかを毎回試す |
| **信頼（「このフォルダを信頼しますか」）を断ると、hook は動かない** | 同上。README で「必ず承諾」と案内している |
| **プログラム（Python など）が書くファイル** | 規則（実行前に書き出し先を確かめる）と、フルパスでの報告 |
| hook の設定は、セッション中に書き換えると即座に反映される | AI が設定ファイルを直接書くことは hook と `deny` で止まる。プログラム経由の書き換えは `疎通確認` 8-1 で発見する |
| 書き込み1回ごとに PowerShell を起動する | 実測で1回 0.5 秒前後。許容範囲と判断 |

### どう確かめたか

- **単体試験（40通り）**: 仮インスタンスに対して判定だけを走らせた。`out` の中・`PROFILE.md`・スキルは通り、
  `task.md`・ルートの `out`・設定ファイル・別インスタンス・ジャンクション経由・`..` での脱出・代替データストリーム・
  UNC などはすべて止まった。200万文字の書き込み内容でも 0.6 秒前後
- **実機試験**: Claude Code 2.1.270 と 2.1.197 に配布物の `settings.json` を読ませ、`acceptEdits` モード
  （作業フォルダ内の編集が自動承認される）で書かせた。`out` の中は書け、`task.md`・`00_疎通確認` 直下・
  作業フォルダに加えた外部フォルダへの書き込みは、**hook のメッセージで止まり、ファイルは変わらなかった**
- **未確認**: 実際のインスタンスでの `疎通確認`（信頼ダイアログを通した状態）、プランモードとの相性

## 15. ネットワークドライブで、履歴の一覧が空になる問題（1.1.0）

### 症状と原因

AI-DESK をネットワークドライブ（`Z:` など）に置くと、VS Code の Claude Code で、履歴の一覧が空になります。
**Claude Code 側の不具合です。** 公開の不具合報告もあります（anthropics/claude-code の #31219・#33140・#63527 など）。

- Claude Code は履歴を `.claude\projects\<作業フォルダのパスの英数字以外を - にした名前>\` に保存する
- **保存する側は `Z:\...` のまま**名前を作る
- **VS Code 拡張は、一覧を探す前に実体のパス（`\\サーバー\共有\...`）に解決する**
- 名前が食い違い、探す先のフォルダが存在しないので、一覧が空になる

旧構成でも同じことが起きており、そのときは PC ごとに手でジャンクションを作って直していました。

### どう直したか

`bin\setup_history.ps1` を配布物に入れました。「一覧が探す名前」で「実際の保存先」を指す
ジャンクションを1本作ります。**PC ごと・インスタンスごとに1回**必要です。

**そのうえで、セッション開始時の hook（`SessionStart`）で、毎回 `-Quiet` で自動実行します。**
履歴は PC ごとに保存されるので、その PC で最初のセッションを始めた時点で入口ができます。
**履歴が溜まる前に直るため、利用者は症状に出会いません。**

- 移動・削除・上書きをしない。既に別のリンクや本物のフォルダがあれば、何もしない
- `-Quiet` は何も表示せず、常に終了コード 0 で終わる。
  `SessionStart` の標準出力は AI の文脈に入り、0 以外の終了コードは利用者にエラー表示が出るため
- 対象は `startup` と `resume`。`/clear` や圧縮のたびには走らせない
- 自動で直らなかったとき（信頼していない、hook が止められている など）は、`疎通確認` の 10 が見つける。
  AI が手で実行するときは**ユーザーの承諾を得てから**（`setup_python.ps1` と同じ扱い）
- Claude Code 側で直っても、ジャンクションは同じフォルダを指すだけなので無害

**利用者に聞かずにユーザーのフォルダへ書き込む**ことになりますが、書くのはジャンクション1本だけで、
管理者（配布物）の判断として採りました。AI が自分の判断で書き込むのとは区別しています。

### AI-DESK 以外でも使えるようにした

同じ症状は、AI-DESK に限らず、ネットワークドライブ上のフォルダで Claude Code を使えば起きます。
そこで `setup_history.ps1` を**単体でも使える形**にしました。

- 既定の対象は「いまの作業フォルダ」。AI-DESK の中に置かなくても動く
- ファイルの先頭に **AI 向けの手順**（調べる → 承諾を得て直す → 開き直しを案内する）を書いた。
  利用者は、このファイルを添付するかフォルダに置いて「これを実行して」と頼むだけでよい
- `-All` で、この PC の履歴にあるネットワークドライブ上のフォルダをまとめて直せる。
  フォルダ名からは元のパスを戻せないため、履歴ファイルに記録された作業フォルダを読み、
  そこから作った名前がフォルダ名と一致するものだけを対象にする

**形態として、スキルは採りませんでした。** スキルは PC ごと・プロジェクトごとに置く手間があり、
「困ったときに1回渡す」使い方に合わないためです。
AI が手順書（Markdown）を読んで毎回コマンドを書き起こす方式も、結果がぶれるため採りませんでした。
**決まった処理はスクリプトに、判断と説明は AI に**、という分担です。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| `CLAUDE_CODE_PROJECT_DIR_NAME` で保存先の名前を固定する | `CLAUDE_CONFIG_DIR` も必要で、**起動前に環境変数で設定しなければならない**（設定ファイルの `env` では効かない）。利用者に起動のしかたを変えさせることになる |
| `\\サーバー\共有\...` で直接開いてもらう | コマンドプロンプトなど、UNC を作業フォルダにできない道具がある。`PROFILE.md` や過去の記録も `Z:\` の書き方 |
| AI-DESK をローカルに置くよう求める | 共有フォルダに置けることは、AI-DESK の利点の1つ（→ 4） |
| `new-instance.ps1` で自動で行う | 作った人の PC にしか効かない。使う PC ごとに要る |
| AI が承諾を得て手で実行するだけにする | 症状に気づいてからでないと直らない。気づかないまま「履歴が消えた」と思われる |

### あわせて直したこと — hook の、パスの書き方の違い

同じ系統の不具合報告に、**デスクトップ版の Claude Code が `Z:` を `\\サーバー\共有\...` に解決する**ものがあります（#44152）。
書き込み制限の hook は、インスタンスのルートと書き込み先を比べるため、
**片方が `Z:\...`、もう片方が `\\サーバー\共有\...` だと、`out` への書き込みまで止めてしまいます。**
止める側に倒れるので危険ではありませんが、何も出力できなくなります。

そこで、**2つの書き方が混ざったときだけ、両方を `\\サーバー\共有\...` に揃えてから比べる**ようにしました。
揃えるのは、ドライブの割り当て（`Get-PSDrive` の `DisplayRoot`）から分かる範囲だけです。

### どう確かめたか

- `setup_history.ps1`: 作業用の仮の置き場で17通り（調べるだけ・作成・再実行・既存の履歴が見えるか・
  本物のフォルダがある場合・別のリンクがある場合・ローカルの場合・存在しないフォルダ・
  `-Quiet` で何も表示せず 0 で終わるか・既定の対象が作業フォルダか・`-All` が一致するフォルダだけを直すか）
- hook: 実際のドライブの割り当てを使い、`Z:\...` と `\\サーバー\共有\...` を混ぜた10通りの判定。既存の40通りも再実行
- `SessionStart`: Claude Code 2.1.270 で、配布物と同じ呼び方（`${CLAUDE_PROJECT_DIR}` と `-Quiet`）のまま、
  対象と履歴の置き場だけを試験用に差し替えて起動した。**セッション開始時にジャンクションができ、
  エラー表示も AI への余計な出力も無かった**
- 実機: 利用者の PC で、Z: 上のテスト用インスタンスの履歴が、一覧に出るようになった（手で作ったジャンクションによる）
- **未確認**: 新しい PC で、自動実行だけで一覧に出ること

## 16. 依頼のひな形を整理し、数字付きの `out` にも書けるようにした（1.1.0）

### ひな形の置き場を `00_タスクテンプレート\` にした

`task_template\` を `00_タスクテンプレート\` に、`task.md` を `TASK.md` に、`Readme.md` を `README.md` に改めました。

- **特別なフォルダだと、ひと目で分かるようにするため**です
- 頭の `00_` で、エクスプローラーでは業務のタスクフォルダ（`202610_…`）より上に並びます。点検用の `00_疎通確認` と同じ付け方です
- **`TASK.md` の大文字・小文字は問いません。** Windows のファイル名は大文字・小文字を区別しないため、既存の `task.md` も同じ名前で読めます。
  ただし、検索の道具が区別することがあるので、`CLAUDE.md` では「見つからなければフォルダの中を一覧して確かめる」と定めました
- hook と `deny` は、**旧名の `task_template` もテンプレートの置き場として扱い続けます。**
  `update-instance.ps1` は削除をしない（→ 9）ので、1.0.0 から更新したインスタンスには旧フォルダが残ります。
  扱いを外すと、そこがタスクフォルダと見なされ、`task_template\out\` に書けてしまいます

### ひな形の項目を減らした

並びは「概要 → 見る場所（場所と説明）→ 依頼事項、考慮事項 → 注意してほしいこと → ここまで出来ていれば完成という条件」です。

| 廃止した項目 | 代わり |
|---|---|
| 見なくてよい場所 | **「見る場所」に書かれていない場所は、見ない場所**とした。見る必要が出たら、AI が開く前に確認する |
| 欲しいもの（形） | 「依頼事項、考慮事項」の中に書く（ひな形の説明に、形式・分量・読み手を書くよう添えた） |

- 除外を列挙する書き方では、**書く人が除く場所を思いつけなければ、そこも読まれます。**
  「書いた場所だけを見る」形なら、書き漏れても読まれる範囲は広がりません
- 「見る場所」が手がかりだけ（「設備関係の資料」など）のときは、AI が場所を探し、**どこを読むかを伝えてから**読みます
- **以前のひな形で書かれた依頼も、そのまま受け付けます。** `CLAUDE.md` に、以前の項目の読み替え表を置きました

### 数字付きの `out`（`out2`, `out3` …）にも書けるようにした

2回目以降のやりとりで「**更新したファイルを out2 に作って**」のように、前回の成果物と分けて出させたいためです。

| 決めたこと | 理由 |
|---|---|
| **`out` の後ろに数字だけ**を許す（`out`, `out2`, `out10` …）。大文字・小文字は問わない | `out` で始まる名前すべてを許すと、`output_業者提出` のように**人が資料を置いたフォルダにも書けてしまう**。判定は `^out[0-9]*$`（全角の数字は許さない） |
| **ユーザーが指定したときだけ**使う。AI が自分の判断で作らない | 散らかるため。整理は、これまでどおり `out` の中の階層で行う |
| 指定は同じ会話の中で続き、新しい会話で指定が無ければ `out` に戻る | 前の会話の指定を引きずると、どこに出たか分かりにくい。どちらに出すかは「出力先:」の宣言で毎回示す |
| 作業記録（`00_作業記録.md`）は、どこに出した回も **`out\` の1つ**にまとめる。回次の番号も通しで数える | `継続タスク` が読む場所を1つに保つため |
| ルート直下の `out2` なども、ルート直下の `out` と同じく**タスクフォルダと見なさず、`deny` にも挙げる** | 「out2 に出して」をルート直下と取り違えるのは、実際に起きた事故（ルート直下の `out` に出した）と同じ型のため |

`settings.json` には、`allow` に `Edit(*/out[0-9]*/**)`、`deny` に `Edit(/out[0-9]*/**)` を足しました。
gitignore の書き方では `[0-9]*` を「数字1文字の後に何でも」と読むため、`out2abc` にも当たります。
`deny` はルート直下にしか当たらず、`allow` より先に hook が止めるので、判定の本体は hook です。
ただし、**`out` と数字で始まる名前のタスクフォルダ（例: `out2024_報告`）をルート直下に作ると、`deny` で何も書けなくなります。**
名前として考えにくいので、受け入れました。

### どう確かめたか

- **hook の判定（39通り）**: 仮インスタンスで、判定の関数を31通り、hook を別のプロセスとして（標準入力の JSON と終了コードで）8通り。
  `out` / `out2` / `OUT3` / `out10` / `out2\材料\` は通り、`output` / `out_2` / `out2a` / `outline` / 全角の `out２` / `sub\out2` /
  ルート直下の `out2` / `out2\out` / テンプレートの置き場（新旧）/ `bin\out2` / `out2` の中のジャンクション / `..` での脱出は、すべて止まった
- **実機（Claude Code 2.1.197、`claude -p`、`acceptEdits`）**: 配布物の `settings.json` を置いた仮フォルダで、11か所に書かせた
  - hook を止めた状態（`deny` だけ）: ルート直下の `out` / `out2` / `OUT3`、`00_タスクテンプレート`、`task_template` が
    「denied by your permission settings」で止まった。**`[0-9]` を使ったパターンも、日本語のフォルダ名も効き、大文字・小文字も区別しなかった**
  - hook を入れた状態: タスクの `out` / `out2` / `OUT3` / `out10` だけが書け、タスクの `output` と `TASK.md` は hook のメッセージで止まった
- **未確認**: `allow` の `Edit(*/out[0-9]*/**)`。信頼していないフォルダでは `allow` が読み込まれないため（起動時にそう表示された）、この試験では確かめられていない。
  関わるのは確認ありのモードで `out2` への書き込みに確認が出るかどうかだけで、書き込み先の制限には関わらない

## 17. プロンプトから直接依頼を受けられるようにした（1.1.0）

### きっかけ

依頼のたびに **(1) フォルダを作る → (2) `TASK.md` を書く → (3)「〜をやって」と頼む** の3手が要りました。
毎月の集計のように繰り返す依頼には見合いますが、**一度きりの依頼には重すぎます。**

チャットでそのまま頼めば、AI がタスクフォルダを作って作業する形を足しました。

### `TASK.md` を AI に書かせなかった

**この判断が、この節の中心です。**

「A と B と C を自動化する」と考えると、素直な設計は「AI が `TASK.md` を書く」になります。
そうしませんでした。理由は3つです。

**1. 出所が混ざる。**
`TASK.md` は**人が書く依頼の原本**です。ここに AI の文章が入ると、半年後に読み返したとき
「この条件は人が指定したのか、AI が補ったのか」が**判別できなくなります。**
ファイルを分ければ、その区別が構造として残ります。

**2. 上書き事故が、構造として起きない。**
「新規作成のときだけ許す」実装でも、気をつければ防げます。
しかし**そもそも書けない**なら、気をつける必要がありません。
歯止めを確認や注意から機械的なものへ移す、という 10 と 14 の考え方の続きです。

**3. 「書けるのは `out` の中だけ」という一文が崩れない。**
この一文は AI-DESK の名前の由来そのもので、`CLAUDE.md` の6か所以上、
`00_タスクテンプレート\README.md` の FAQ、`疎通確認` スキル、hook の拒否メッセージに書かれています。
例外を1つ足すと、**そのすべてに例外の説明が要ります。** 規則が長くなり、食い違いが生まれます。

代わりに、AI が聞き取った依頼は `<タスクフォルダ>\out\NN_依頼内容.md` に書きます。
**hook（`guard-write.ps1`）も `settings.json` も、1文字も変えていません。**

利用者への言い方も、これで一貫します。

> プロンプト方式は「**`TASK.md` を書かずに頼む道**」であって、「AI に `TASK.md` を書かせる道」ではない。
> 依頼の原本はチャットのプロンプトそのもの。AI はその聞き取りメモを `out` に残す。

書き起こしを気に入ったら、**人が `TASK.md` にコピーして格上げします。**
「これを依頼として引き受ける」という、人の明示的な行為になります。

### 新しい権限を、1つも足さずに済んだ

タスクフォルダを作ること自体は、**`out` の中にファイルを書けば起きます**（親フォルダが作られるため）。
hook は書き込み先だけを見るので、`<ルート>\差出人名簿\out\01_依頼内容.md` は、
フォルダがまだ無くても通ります（存在しない階層で、リンクの検査は打ち切られます）。

そこで `CLAUDE.md` には「**`mkdir` を別に実行しない**」と書きました。
こうすると、**フォルダの作成が hook の許可の副産物になります。**

規則の変更は1点だけです。絶対遵守ルール1 で読み取り専用としていた「インスタンスのルート直下」に、
「**新しいタスクフォルダを作ることはできる（フォルダだけ。その直下にファイルは置けない）**」を足しました。

### `NN_依頼内容.md` —— 回ごとに1つ、成果物と同じ場所に

最初は「タスクに1つ（`00_依頼内容.md`）」を考えましたが、2つの穴がありました。

| 穴 | `NN` 体系ならどうなるか |
|---|---|
| 同じ回の途中で依頼が増えたとき、上書きか追記か決まらない | 回が進めば新しい番号。回の途中なら同じファイルを更新（→ 下の「回の番号を、依頼と成果物で必ず対にした」） |
| 「回」と「フォルダ」という数える単位が二重になる | 既存の `NN`（回次）に乗るだけで、**新しい概念を足さない** |

結果として `00_` で始まるのは `00_作業記録.md` だけになり、
**「`00_` はタスク全体のもの / `NN_` はその回のもの」**という分類が成立しました。
`out` を開けば `01_依頼 → 01_成果物 → 02_依頼 → 02_成果物` と、依頼と結果が対で並びます。

| 決めたこと | 理由 |
|---|---|
| **成果物と同じフォルダに置く**（`out2` に出す回は `out2\`） | `out2\` だけを開いた人が、`out\` を遡らずに済むため。作業記録の方は、通しの経緯なので `out\` に1つだけ |
| `out\` の番号が飛ぶこと（2回目を `out2` に出すと `01` の次が `03`）は**受け入れる** | 「飛んでいる＝別のフォルダに出した回がある」という手がかりになる。作業記録の成果物欄から辿れる |
| **入り口が `TASK.md` でも書く。ただし要約は作らない** | 1回目だけ無いと、番号が `02` から始まって不揃いになる。一方、原本と要約が並ぶと、読む人が原本の細かい指示を見落とす。書くのは「`TASK.md` のうち今回やる範囲」と「**正は `TASK.md`**」の1行だけ |
| チャットの回は、**言われた言葉の原文をそのまま**書く（中心はここ） | AI の読み取りは誤ることがあるが、原文は誤らない。**チャットの履歴は消える。ここに残したものだけが残る** |
| **作業前**に書く（作業記録は作業後） | 読み取りを誤ったまま長時間作業してしまうのを、ここで防ぐ |
| 作業記録の「依頼」欄は、**1行の要約と参照**に変えた | 言われた言葉を両方に書くと二重管理になり、必ず食い違うため |
| 3つ以上でサブフォルダにまとめる回も、`NN_依頼内容.md` は **`out` 直下に残し、「3つ」にも数えない** | その回の見出しだから。`out` 直下は「ユーザーが読むもの」だけ、という既存の決まりにも合う |

`TASK.md` が無いタスクでは、**`01_依頼内容.md` が「変わらない目的」の記録を兼ねます。**
既存の「目的そのものが変わったときだけ新しいタスクフォルダ」という決まりがあるので、
01 は目的の記録であり続けます。

### フォルダ名を AI が決めることの、危ないところ

| 決めたこと | 理由 |
|---|---|
| `bin` / `out` に数字を付けた名前 / `00_タスクテンプレート` / `task_template` / `.` で始まる名前は**使わない** | **これらを付けると、hook がタスクフォルダと認めず、その中の `out` にすら書けなくなります。** 利用者には理由が分からない止まり方になります |
| Windows の制限（使えない文字、末尾の空白・ドット、`CON` `NUL` などの予約名、260文字） | 作れない、あるいは後で扱えないフォルダになるため |
| **同名のフォルダがあったら、黙って使わない。** 「続きですか、別件ですか」と聞く | 別件なのに前回の作業記録に追記される事故になるため |
| 日付の接頭辞は**付けない** | 次に「〜の続き」と呼ぶための名前だから。呼びやすさを優先する |
| **成果物を作る依頼のときだけ**フォルダを作る。質問や相談では作らない | ルート直下が散らかり、どれが本当の依頼か分からなくなるため |
| フォルダ名は**宣言するが、承諾は求めない** | 往復が増えないことがプロンプト方式の価値だから。名前が気に入らなければ利用者が改名できる（**AI は改名しない** → 絶対遵守ルール4） |

共有フォルダに置かれたインスタンスでは、**フォルダ名が他の人からも見えます。**
取引先名や個人名をそのまま使ってよいかは、迷ったら聞くよう `新規タスク` スキルに書きました。

### 残る穴 —— 正直に書いておきます

- **フォルダの作成そのものは、機械的に止まっていません。** hook が見張るのは `Edit` / `Write` /
  `NotebookEdit` だけで、シェルの `mkdir`（`New-Item -ItemType Directory`）は素通りします。
  これは 1.1.0 以前からある穴で、今回の機能で広がったわけではありません。
  「`mkdir` を別に実行しない」は規則であって、歯止めではありません
- **依頼の読み取りが誤っていても、機械的には止まりません。** `NN_依頼内容.md` を作業前に書くのは、
  誤りを**早く見つけるため**であって、防ぐためではありません
- **`00_` で始まる名前のタスクフォルダを AI が作ると、テンプレートの置き場や点検用と紛らわしくなります。**
  禁止はしていません（`00_タスクテンプレート` だけを除いています）

### 成果物のファイル名で、日付を後ろに移した

    旧: NN_YYYY-MM-DD_名前.拡張子    例: 01_2026-10-15_見積比較_3社版.md
    新: NN_名前_YYYY-MM-DD.拡張子    例: 01_見積比較_3社版_2026-10-15.md

**名前の方が、日付より大事だからです。** エクスプローラーで列の幅が足りないとき、切れるのは末尾です。
旧の形は、幅が狭いと `01_2026-10-15_見積…` となって**肝心の部分から消えます。**

- **回次の `NN` が先頭なのは変わりません。** 1.0.0 で作られた旧形式のファイルと混ざっても、
  **並び順は崩れません。** 旧形式は改名しません（絶対遵守ルール4）。既存の「古いパス表記は書き換えない」に、
  ファイル名の1項を足しました
- 日付が末尾で固定になるので、**名前に `_` が入っていても区切りが曖昧になりません**
- 記録のファイル（`00_作業記録.md` と `NN_依頼内容.md`）には、日付を付けません。
  **「記録のファイルは日付なし、成果物は日付あり」**という分類にしたので、例外にはなっていません

### 回の番号を、依頼と成果物で必ず対にした

受け入れテストで、**前の回の成果物が消える事故**が起きました。
第1回で長すぎる議事録を作り、第2回で「3ページに短くして」と頼んだところ、
短くしたものが**第1回と同じファイル名**で出力され、**第1回の議事録が消えました。**

原因は、規則の側にありました。1.1.0 の途中まで、次の例外を置いていました。

> **推敲中のドラフト**（ユーザーが「ここを直して」と繰り返し磨いているもの）は、
> 同じファイルを更新して構いません。

この例外は「`out` が複製で散らかるのを防ぐ」ために置いたものです。
ところが**「短くして」「書き直して」は、この例外にそのまま当てはまって読めます。**
回をまたいでいるのに、同じファイル名のままになりました。

**例外の側が広すぎたのではなく、境界が「回」ではなく「推敲中かどうか」だったことが誤りです。**
「推敲中か」は AI の解釈に委ねられますが、「回が変わったか」は
**`NN_依頼内容.md` を書いた時点で確定しています。**

| 直したこと | 理由 |
|---|---|
| **`NN` は、その回の `NN_依頼内容.md` と必ず同じ番号**にする | 番号の根拠を、解釈の要らないものに移した。`02_依頼内容.md` を書いた回の成果物は、必ず `02_…` |
| 例外を「**同じ回の中だけ**」に狭めた | 回の途中で仕上げていく間は、同じファイルを更新してよい。`out` が散らかるのを防ぐ当初の目的は、これで足りる |
| 「短くして」「書き直して」「作り直して」を、**名指しで**書いた | この3語が事故の引き金になった。型として書くより、言われた言葉そのもので照合できる方が確実 |
| 実際に起きた事故として、**`CLAUDE.md` と `継続タスク` スキルの両方に書いた** | 「なぜこの規則があるか」が分かる方が、規則は守られる。既存の「過去に実際に起きた間違い」と同じ考え方 |

**失われるもの**（`out` にファイルが増えること）は、意図したとおりです。
回ごとに1つずつ増える並びは、**時系列そのもの**です。
3つ以上出る回は、既存の「`NN_タイトル_YYYY-MM-DD\` にまとめる」で畳めます。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| hook を緩め、`<タスクフォルダ>\TASK.md` の新規作成だけ許す | 上の「`TASK.md` を AI に書かせなかった」の3点。とくに、hook・`settings.json`・`CLAUDE.md` 6か所以上・`README.md` の FAQ・`疎通確認`・拒否メッセージのすべてに例外の説明が要る |
| `bin\new-task.ps1` を足し、承諾を得て実行させる | 日本語の長文を PowerShell に渡す部分が壊れやすい。「スクリプト経由なら `out` の外に書ける」という抜け道の前例を広げる |
| 依頼を別ファイルにせず、`00_作業記録.md` の「依頼」欄を厚くする | 作業記録は**作業後**に書くもので、依頼の読み取りは**作業前**に確定させたい。`out2` に出した回の依頼が `out2` から見えない |

### どう確かめたか

- **hook の判定**: `<ルート>\差出人名簿\out\01_依頼内容.md` は、タスクフォルダがまだ存在しない状態でも通ること
  （`Get-WriteDecision` の階層をたどる検査が、存在しない階層で打ち切られること）を、16 の試験環境で確認
- **`<ルート>\差出人名簿\TASK.md` は止まること**（2階層しかないため）。16 の実機試験で、
  タスクの `TASK.md` が hook のメッセージで止まることは確認済み
- **未確認**: 実機でのプロンプト方式の通し。フォルダの自動作成（`Write` が親フォルダを作ること）は、
  受け入れテストで確かめる必要があります

## 18. 成果物をタスクフォルダ直下に出し、依頼と成果物を `A` / `B` で対にした（1.2.0）

### きっかけ

1.1.0 を実機で2件使ってみて、2つのことが分かりました。

**1. タスクフォルダが、階層として仕事をしていない。**
プロンプト方式で作ったタスクフォルダの下には、`out\` しかありませんでした。
成果物を開くのに、**タスクフォルダと `out` の2つを開く**ことになります。
`00_TASK.md` を置く場合でも、タスクフォルダにあるのは依頼と `out` だけです。

**2. プロンプト方式が、標準の使い方になった。**
17 では「一度きりの依頼のための道」として足しましたが、実際には**ほとんどの依頼がこちら**でした。
`00_TASK.md` を前もって書くのは、繰り返す依頼と、話し言葉で伝えきれない依頼だけです。

そこで、**出力先をタスクフォルダの直下に移し、`out`（`out2`・`out3` も）を廃止**しました。
あわせて、文書の書き方も「プロンプトがふつう、`00_TASK.md` は例外」に入れ替えました。

### `out` をやめると、歯止めの定義が「肯定形」から「否定形」に変わる

**これが、この節でいちばん大事な点です。**

1.1.0 までの hook は、**`out` という名前のフォルダを目印**にしていました。

    書ける = <ルート>\<タスクフォルダ>\out\ の中

`out` は「出力」以外の意味を持ちません。だから**肯定形で一文にできます。**
これが AI-DESK という名前の由来そのものでした。

タスクフォルダの直下に出すと、場所だけで判定する限り、定義はこうなります。

    書ける = ルート直下のフォルダのうち、bin でも 00_タスクテンプレート でも「.」始まりでもないものの中

**除外リストで決まる、否定形の定義**です。具体的に3つ壊れます。

| 壊れるもの | なぜ |
|---|---|
| **人が書いた `00_TASK.md` を、AI が上書きできる** | 1.1.0 までは2階層しかないので hook が止めていた。これは 17「`TASK.md` を AI に書かせなかった」を支えていた壁で、上書きは元に戻せない |
| **ルート直下に資料フォルダを置いている人がいると、その中に直接書ける** | 1.1.0 までは `参考資料\out\` にしか書けなかった（変な場所だが無害だった） |
| **`疎通確認` 8-4 が対象を失う** | `00_疎通確認\hook確認.md`（`deny` に無く、hook だけが止める場所）が、書ける場所になってしまう |

### 直し方 —— hook を、場所だけでなく「名前」でも判定させた

タスクフォルダの中で書いてよい名前を、次だけにしました。

| 許すもの | 名前 |
|---|---|
| タスク全体の記録 | `00_` で始まるファイル（`00_作業記録.md` など）。**ただし `00_TASK.md` は除く** |
| その回の依頼と成果物 | `NNA_` / `NNB_` で始まるファイル |
| 1回で3つ以上出すときのまとめ先 | `NNB_` で始まるフォルダの中 |
| スクリプト・中間データ | `材料\` の中 |

これで、**書ける場所をふたたび肯定形で言えます。** しかも**1.1.0 より狭い**（`out` の中は名前が何でもよかった）。

- `00_TASK.md` は名前が合わないので、**機械的に**守られます
- ルート直下に置かれた資料も、名前が合わないので上書きされません
- 8-4 の対象は `00_疎通確認\メモ.md`（名前が合わないもの）に置き換えました

**副産物として、命名規則そのものが機械で守られるようになりました。**
`out` 方式では得られなかった利得で、「歯止めを注意から機械的なものへ移す」という
10・14・17 の流れの続きです。

代償は、hook が複雑になることと、規則に合わない名前を出そうとしたときに止まることです。
後者は、**拒否の文に「`NNB_内容を表す日本語名_YYYY-MM-DD.拡張子` の形にしてください」と書いて**解決しました。
`out\` へ書こうとしたときも、「この版では `out` を使いません」と名指しで返します。

`deny` にも `Edit(*/00_TASK.md)` を足し、2枚目の壁にしました。
`Edit(/out/**)` などは、`out` という概念ごと無くなったので外しました。
**使われない概念を設定に残すと、規則の側が嘘をつき始めるためです。**

### `A` / `B` —— その回の依頼が、その回の成果物のすぐ上に来る

    1.1.0: 01_依頼内容.md / 01_見積比較_3社版_2026-10-15.md
    1.2.0: 01A_依頼内容.md / 01B_見積比較_3社版_2026-10-15.md

1.1.0 の形では、`01_` の後ろが日本語なので、**並び順が名前次第で入れ替わりました。**
`A` / `B` を挟むと、**依頼が必ず成果物の上**に来ます。

| 決めたこと | 理由 |
|---|---|
| `A` が依頼、`B` が成果物 | 並び順がそのまま「頼む → 出る」の順になる |
| `01A` の結果は `01B`、`02A` の結果は `02B` | 17 で作った「回次」の体系に乗るだけ。**新しい概念を足さない** |
| `00_作業記録.md` は `00_` のまま（`00B_` にしない） | 「`00_` はタスク全体のもの / `NN` はその回のもの」という既存の分類を崩さないため。`A` / `B` は「回」の中の区別 |
| `材料\` は回で分けない | スクリプトは回をまたいで使い回される。分けると、どの回のものか決められない場面が出る |

**番号の対応は、直したばかりの事故（→ 17「回の番号を、依頼と成果物で必ず対にした」）への
2つ目の手当てでもあります。** 規則で「同じ番号にする」と書くだけでなく、
**名前の形からも見えるようにしました。** `02A_依頼内容.md` の隣が `01B_…` だったら、目で分かります。

### `00_TASK.md` —— 依頼の原本の名前を、1つに絞った

1.1.0 までは `TASK.md` / `task.md` / `task.txt` の3つを探していました。**`00_TASK.md` だけにしました。**

- **`00_` を付けたのは、`01A_` より上に並べるため**です。「`00_` はタスク全体のもの」という分類にも合います
- 探す名前が1つになるので、「見つからないときはタスクフォルダを一覧して確かめる」という
  1.1.0 の但し書きが要らなくなりました。**`00_TASK.md` が無ければ、それはプロンプト方式のタスクです**
- 旧名を読む機能は**残しませんでした。** 移行は管理者が手で行う方針が決まっているためです（下の「残る穴」）

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| 場所だけで判定したまま、`00_TASK.md` は規則で守る | 上書きは元に戻せない。17 で「気をつければ防げるものを、そもそも書けなくした」判断と矛盾する |
| `00_TASK.md` を `00A_TASK.md` にして、`A` / `B` を完全に一貫させる | 人が手で作る唯一のファイルなので、覚えやすさを優先した。`TASK` という語が残る方が、利用者には探しやすい |
| `out` を残したまま、名前だけ `A` / `B` にする | 2階層開く冗長さが残る。きっかけそのものが解決しない |
| 旧 `out\` にも書けるようにして、移行を楽にする | 「使われない概念を設定に残さない」に反する。移行は管理者が手で行う |

### 残る穴 —— 正直に書いておきます

- **回次の番号が正しいかは、hook では見ていません。** 第2回なのに `01B_` と書いても、名前の形は
  合っているので通ります。**規則（→ 「出力と保存のルール」2）だけが頼り**です
- **1.1.0 以前のインスタンスは、自動では移行しません。** `out\` の中のファイルは、
  そのままでは AI から書けなくなります。**管理者が手で片付ける前提**です。
  `疎通確認` 9 は、`out\` や `task_template\` が残っていても異常とはしません
- **ルート直下のフォルダは、依然として「除外リスト」で決まります。** 名前の判定が入ったことで
  被害は小さくなりましたが、ルート直下に置かれた資料フォルダに `01B_…` という名前で
  書き込むことは、理屈のうえでは可能です
- **フォルダの作成そのものは、機械的に止まっていません**（17 から変わらず）

### どう確かめたか

- **hook の判定（44通り）**: `Get-WriteDecision` を直接呼ぶ試験。
  `01A_` / `01B_` / `00_作業記録.md` / `材料\` の下 / `NNB_` フォルダの下 / 3桁の回次 / `PROFILE.md` /
  `.claude\skills\` は通り、`00_TASK.md`（大文字・小文字とも）/ 旧 `TASK.md` / `task.txt` / `メモ.md` /
  1桁の回次 / `01C_` / `A` / `B` 無しの `01_` / `資料\` の下 / `02A_` フォルダの下 /
  タスクの `out`・`out2`・`OUT` / ルート直下の `out`・`out2`・`OUT3`・`out10` / ルート直下のファイル /
  `bin` / `00_タスクテンプレート` / `.claude\settings.json` / `.ai-desk\` / AI-DESK の外 /
  `..` での脱出は、すべて止まった
- **別プロセスとして（11通り）**: 仮インスタンスを作り、標準入力の JSON と終了コードで確認。
  まだ存在しないタスクフォルダへの書き込みが通ること、相対パスが cwd 基準で解決されること、
  `00_TASK.md` の拒否メッセージが「人が書く依頼の原本です」と名指しで返ることを確かめた。
  **仮インスタンスにファイルが1つも作られないこと**も確認済み
- **未確認**: 実機での通し（`claude -p` での書き込み）と、`settings.json` の
  `allow`（`Edit(*/[0-9][0-9]B_*)` など）。`allow` は確認ありのモードでの手数に関わるだけで、
  書き込み先の制限には関わらない

## 19. 1つの成果物を、回をまたいで直していけるようにした — 育てるファイル（1.3.0）

> **1.5.0 で取りやめました**（→ 21）。当時の判断の記録として残します。

### きっかけ

1.2.0 では、回ごとに `01B` → `02B` → `03B` と**別のファイル**になります。
議事録や提案書のように、1つのものを何回も話し合って仕上げる使い方では、
直下に版違いが並び、**どれが最新かを毎回探す**ことになりました。

一方、1.2.0 で「同じファイルを直してよい」例外を「同じ回の中だけ」に狭めたのは、
**前の版が消えた事故**が理由です（→ 17「回の番号を、依頼と成果物で必ず対にした」）。
守るべきことは2つでした。

1. **前の版が消えないこと**
2. **切り替えの境界を、AI の解釈に任せないこと**

### 形 —— 直下には1つ、版は `材料\` に

    議事録\
        00_作業記録.md
        00_議事録.md                 ← 育てるファイル
        01A_依頼内容.md
        02A_依頼内容.md
        材料\
            01B_議事録_2026-10-15.md  ← 第1回の仕上がりの控え
            02B_議事録_2026-10-16.md  ← 第2回の仕上がりの控え

| 決めたこと | 理由 |
|---|---|
| 名前は **`00_[日本語名].拡張子`** | `00_` は「タスク全体のもの」という 17 の分類に、そのまま乗る。回をまたぐファイルなので回次を持たない |
| **日付を付けない** | 回をまたぐため。日付は控えの名前に入る。「記録は日付なし、成果物は日付あり」の分類からは外れるが、日付の情報は失われない |
| **回の終わりに `材料\NNB_…` へ写す** | 番号の対（`02A` ↔ `02B`）を、`材料\` の側で保てる。控えの名前を決めるのに新しい規則が要らない（ふだんの `NNB_` の命名と同じ） |
| **書き換える前に、前の回の控えがあることを確かめる** | 回の終わりに写し忘れても、**消える直前**に気づける。事故が起きる瞬間に確認を置いた |
| 控えの置き場は **`材料\` の直下** | `材料\` は、もともと「バックアップ」の置き場。新しいフォルダ名を増やさない |
| 写すのは **`Copy-Item`** | xlsx・docx を壊さずに写せる。Read / Write では、バイナリを写せない |
| 途中から切り替えるときは、**いちばん新しい `NNB_…` を写して始める** | それまでの `NNB_…` は改名も移動もしない（絶対遵守ルール4） |
| 対象は**ファイル1つだけ** | 3つ以上出る回の `NNB_` フォルダまで育てると、控えの取り方が一気に複雑になる |

### 切り替えの境界 —— 作業記録の1行

**ユーザーの承諾があったときだけ**切り替えます。AI は、**同じ成果物を2回続けて直した回**に
「次にできること」の1つとして提案して構いません。

決まったら、`00_作業記録.md` の `## 毎回守ること` に1行書きます。

    - 議事録は `00_議事録.md` を直していく（第3回から。各回の控えは `材料\`）

**次の回は、この行があるかどうかだけで判断します。**
1.1.0 の事故は、「推敲中か」という AI の解釈に境界を置いたことが原因でした（→ 17）。
ここでは、境界を**書かれた1行の有無**に置きました。`## 毎回守ること` は毎回読む欄なので、
新しい欄も新しいファイルも足していません。

### 新しい権限を、1つも足さずに済んだ

hook（`guard-write.ps1`）は、もともと `00_` で始まるファイルと `材料\` の中への書き込みを許しています。
**判定のロジックは1文字も変えていません**（冒頭のコメントだけ直しました）。

### 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 今の `NNB_` のまま、作業記録の「いまの状況」で最新を示すだけ | 直下に版違いが並ぶ問題が残る。「どれを開けばよいか」を毎回作業記録で調べることになる |
| 控えを取らずに `00_[名前]` を上書きしていく | いちばん単純だが、1.1.0 の事故と同じことが起きる |
| `材料\版\` という専用のフォルダを作る | 混ざらない利点はあるが、名前の決まりが1つ増える。`NNB_` の名前で十分に見分けられる |
| hook が書き込みの前に、自動で控えを取る | hook は「何も書かない」作り。歯止めの側が書き込みを始めると、歯止めの検証が難しくなる |
| AI が自分の判断で切り替える | 境界が AI の解釈に戻る。1.1.0 の事故の型そのもの |

### 残る穴 —— 正直に書いておきます

- **控えを写すのは、規則であって歯止めではありません。** hook は書き込み先を見るだけで、
  写したかどうかは分かりません。「書き換える前に確かめる」で、事故の直前に気づける形にしただけです
- **`00_` のファイルは、以前から AI が書けます。** 控えを取らずに上書きされる余地は、1.2.0 と同じだけ残ります
- **`Copy-Item` はシェルのコマンドなので、hook では止まりません。** 写し先がタスクフォルダの中かは、
  AI の確認だけが頼りです
- **確認ありのモードでは、育てるファイルの書き込みのたびに確認が出ます。**
  配布物の `settings.json` の `allow` に、`00_作業記録.md` 以外の `00_` の名前が入っていないためです。
  書き込みの制限には関わりません

### どう確かめたか

- **hook の判定（10通り）**: `Get-WriteDecision` を直接呼ぶ試験。
  `00_議事録.md` / `00_見積比較.xlsx` / `材料\01B_…` / `材料\03B_….xlsx` / `00_作業記録.md` / `02A_依頼内容.md` は通り、
  `00_TASK.md` / 接頭辞のない `議事録.md` / ルート直下の `00_議事録.md` / `版\` の下は止まった
- **未確認**: 実機での通し（第1回 → 第2回「短くして」→ 提案に承諾 → 第3回）

## 20. 保管フォルダ `_保管*` —— 古いタスクフォルダを、まとめて置けるようにした（1.4.0）

### きっかけ

タスクフォルダは、インスタンスのルート直下に1件ずつ増えていきます。
使い続けると直下が長くなり、**いま使っているタスクが見つけにくくなりました。**
古いものを `old\` などに移したくなりますが、1.3.0 までの hook と規則では、次の2つが起きます。

1. **`old` そのものがタスクフォルダと見なされる。** hook は、ルート直下のフォルダを（決まった例外を除いて）
   すべてタスクフォルダとして扱うため、`old\01A_依頼内容.md` が書けてしまう
2. **「〜の続き」で見つからない。** AI はルート直下しか探さないので、同じ名前の新しいタスクを作り直してしまう

### 形 —— `_保管` で始まる名前を、入れ物の印にした

    <インスタンスのルート>\
        差出人名簿\               ← タスクフォルダ
        _保管庫_仕事\             ← 保管フォルダ（それ自体はタスクフォルダではない）
            202610_見積比較\       ← タスクフォルダ（保管中）。その場で続けられる
        _保管庫_趣味\
            旅行の計画\

| 決めたこと | 理由 |
|---|---|
| **名前が `_保管` で始まる**フォルダを保管フォルダとする（1つの名前に決めない） | 用途別に `_保管庫_仕事`・`_保管庫_趣味` と分けられる。判定は接頭辞1つで済む |
| 保管フォルダの**直下のフォルダを、タスクフォルダとして扱う**（書ける） | 続けるたびにルート直下へ戻す手間をなくす。目的は「見通し」であって「書けなくすること」ではない |
| 保管フォルダの**直下にファイルは置けない**。**入れ子は作れない**（1段だけ） | 判定の形が「ルート直下」と「保管フォルダの直下」の2通りで終わる。AI の探す範囲も2通りで済む |
| 保管フォルダへの**出し入れは人が行う** | 絶対遵守ルール4（AI は移動しない）のまま |
| 新しいタスクフォルダは**必ずルート直下**に作る。`_保管` で始まる名前は使わない | 保管フォルダの中に新しいタスクが紛れ込まないように。名前の禁止は `bin`・`out` と同じ扱い |
| 配布物に **`_保管庫\README.md`** を入れる | 規則を読まない人でも、置き場があれば使える。空のフォルダは Git も配布のスクリプトも写さないため、案内のファイルを1つ置いた |

### 「〜の続き」と言われたときの探し方

探すのは、**ルート直下と、各保管フォルダの直下だけ**です。

| 言われ方・見つかった場所 | どうするか |
|---|---|
| 保管フォルダまで言われた（「`_保管庫_仕事\見積比較` の続き」） | 確かめずに続ける |
| ルート直下にだけある | 確かめずに続ける（1.3.0 までと同じ） |
| 保管フォルダの中に1つだけある | 「`_保管庫_仕事\見積比較` のことですか」と聞く |
| 2か所以上にある | 候補を並べて聞く |

保管フォルダの中にしか無いときに**確かめる**のは、ユーザーが保管したことを忘れて、
同じ名前で別件を頼んでいる可能性があるためです。場所まで言われたときは、その心配がないので確かめません。
新しいタスクを作るときの「同じ名前があったら聞く」も、保管フォルダの中まで広げました。

### hook の判定

`Get-TaskFolderDepth` を足し、ルートからの並びのうち何番目までがタスクフォルダかを返すようにしました。

- 1つ目がタスクフォルダの名前 → 1（これまでどおり）
- 1つ目が `_保管…` で、2つ目がタスクフォルダの名前 → 2
- それ以外 → 止める（保管フォルダの直下のファイル、入れ子、`bin` などの禁止名は、名指しの理由を返す）

タスクフォルダの中の名前の判定（`Get-NameDecision`）は、**1文字も変えていません。** 深さが変わるだけです。

### 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| `old\` のように、名前を決めずに人に任せる | `old` がタスクフォルダと見なされる。AI も探せない |
| 保管フォルダの中を**書けなくする**（続けるときは人が戻す） | いちばん単純で安全だが、続けるたびに戻す手間がかかる。利用者が「その場で続けたい」を選んだ |
| AI-DESK の外（`AI-DESK_保管\` など）に置く | 規則の変更は要らないが、目につきにくく、続けるには戻す必要がある |
| 保管フォルダの入れ子（`_保管庫\2025年\見積比較\`）を認める | 判定と探す範囲が深さの分だけ広がる。用途別の分け方は、`_保管` で始まる名前を増やせば足りる |

### あわせて行ったこと

- **人向けの文書の「依頼フォルダ」を「タスクフォルダ」にそろえました。** AI 向けの `CLAUDE.md` は「タスクフォルダ」、
  人向けの README は「依頼フォルダ」と、同じものを2つの名前で呼んでいたためです。README の初出で意味を説明しています
- **`疎通確認` に「Windows で動いているか」（1-2）を足しました。** hook は `powershell.exe` で起動するため、
  macOS や Linux では起動できず、**止まるのではなく、制限なしで書けてしまいます**（→ 12）。
  気づかずに使われるのを防ぐため、Windows 以外なら「異常」と報告します。`CLAUDE.md` の「実行環境について（Windows）」の冒頭にも同じことを書きました

### 残る穴 —— 正直に書いておきます

- **`publish.ps1` と `new-instance.ps1` は、配布物のフォルダの中のファイルをすべて写します**（`.gitignore` は見ません）。
  開発リポジトリの `AI-DESK\_保管庫\` に本物のタスクを置くと、そのまま配られます。
  これはルート直下のタスクフォルダでも同じで、今回新しく生まれた穴ではありませんが、`_保管庫` は物を置きたくなる名前です
- **`_保管庫\README.md` は、更新のたびに配られます。** 利用者が `_保管庫` を改名したり消したりしていても、
  `update-instance.ps1` で更新すると、`_保管庫\README.md` がまた作られます。害はないので、README にそう書いて済ませました
- **「〜の続き」の探し方は規則であって、hook では見ていません。** hook は「どのタスクか」を知らず、
  ルート直下でも保管フォルダの中でも、タスクフォルダなら書けます（1.3.0 までと同じ考え方です）
- **確認ありのモードでの手数**: 配布物の `settings.json` の `allow` は、深さの違う保管フォルダの中でも当たるかを確かめていません。
  当たらなくても確認が出るだけで、書き込みの制限には関わりません

### どう確かめたか

- **hook の判定（38通り）**: `Get-WriteDecision` を直接呼ぶ試験。
  これまでの判定（`01A_` / `01B_` / `00_` / `材料\` / `NNB_` フォルダ / `PROFILE.md` / `.claude\skills\` が通り、
  `00_TASK.md` / 決まりにない名前 / `out` / `bin` / `00_タスクテンプレート` / `.ai-desk` / ルート直下のファイル / `..` での脱出が止まる）が
  変わらないこと、`_保管庫\<タスク>\` と `_保管庫_仕事\<タスク>\` の中の決まった名前が通ること、
  保管フォルダの直下のファイル・保管フォルダそのもの・入れ子・保管フォルダの中の `bin` / `out` / `.` で始まる名前 /
  `00_タスクテンプレート`・保管中のタスクの `00_TASK.md` と決まりにない名前・`..` での脱出が止まることを確かめた
- **別プロセスとして（6通り）**: `new-instance.ps1` で仮のインスタンスを作り、`_保管庫\README.md` が配られることと、
  標準入力の JSON と終了コードで判定が同じになることを確かめた。**仮のインスタンスにファイルが1つも増えないこと**も確認済み
- **未確認**: 実機での通し（保管したタスクを「〜の続き」で呼ぶ、場所まで言って呼ぶ、2か所に同じ名前がある）

## 21. 育てるファイルをやめ、直すファイルと名前を利用者が決められるようにした（1.5.0）

### きっかけ

1.3.0・1.4.0 を試験用のインスタンスで通しました。動きは規則どおりで、切り替え・控え・保管フォルダの中での継続も
食い違いはありませんでした（控えの中身はハッシュで突き合わせた）。

ただ、**AI からの切り替えの提案が、慣れない人には読み解きにくいものでした。**

> 次の回から `00_議事録.md` の1つを直していく形にする（これまでの版は `材料\` に控えとして残ります）

「次にできること」は番号で選ぶ場所です。そこに仕組みの説明が混ざり、選んだら何が起きるのかが分かりません。
試験でも、承諾したつもりの返事を AI が承諾と受け取らず、1回足踏みしました（AI の判断は規則どおりでした）。
利用者の判断は「**簡単な操作が良い**」です。

### 方針 —— 原則は決めておき、求めがあれば AI が判断する

利用者の言葉で書くと、次のとおりです。

> 基本的な振る舞い（原則として 00 → 01 → 02 …）を定めながらも、利用者からの求めがあった場合には、
> AI が許される範囲で自主的に最善を判断してくれた方が良い。
> 「AI-DESK の外のフォルダに書くことができない」というルールが重要で、それが守られる限り、事故のリスクは限定的。
> 使ってみて事故が多発する場合には考える。

| 決めたこと | 理由 |
|---|---|
| 原則は 1.2.0 のまま（回ごとに `NNA`/`NNB`）。**AI から出し方を変える提案はしない** | 提案そのものが分かりにくかった |
| **利用者が直すファイル・出す名前を決めたら従う。** タスクフォルダの直下なら名前は自由 | 名前を決める権利は利用者にある。「今後は 02B を直して」でも「直すファイルを 00_議事録 として」でもよい |
| 「今後は」「今回だけ」の範囲は、**AI が言葉の意味から判断する** | 1.3.0 は「`毎回守ること` の行があるかだけで判断」と決定論的に縛った。今回は、その時点で AI が意味を汲む方を選んだ |
| 次の回にも続く指定は、`## 毎回守ること` に1行書く | 新しい会話の AI が知る手段が、作業記録しかないため。判断の材料であって、hook の鍵ではない |
| 直す前の版を `材料\<元の名前>_第NN回の前.拡張子` に残す | 1.2.0 の事故（「短くして」で前の版が消えた）への答えは保つ。AI の作業なので、利用者は知らなくてよい |
| `00_作業記録.md`・`NNA_依頼内容.md` は直していく対象にしない | 経緯と依頼の記録という役目があるため。hook では止めず、決まりで断る |
| 1.3.0 の「`00_議事録.md` を直していく」の行は、利用者の指定として読む | 試験用インスタンスを含め、そのまま続けられる |

控えの名前を、1.3.0 の `材料\NNB_…`（回の終わりの仕上がり）から `_第NN回の前`（直す前）に変えたのは、
**指定されたのが既存の `02B_…` でも、新しい `議事録.md` でも、同じ手順で済むため**です。
1.3.0 の「前の回の控えがあるか確かめる」「切り替えた回は写さない」という分岐が要らなくなりました。

### hook —— タスクフォルダの直下のファイル名を見なくした

hook には「**利用者が指定したかどうか**」が分かりません。見ているのは書き込み先だけで、会話は見えないからです。
利用者の指定で `議事録.md` を許すには、3つの案がありました。

| 案 | しくみ | 採らなかった理由／採った理由 |
|---|---|---|
| **A. 直下の名前の制限をやめる（採用）** | 直下は `00_TASK.md` 以外、どんな名前でも書ける。「指定があったときだけ」は決まりで守る | 利用者の方針（上）。いちばん大事な歯止め（タスクフォルダの外に書けない）は残る |
| B. `毎回守ること` の1行を hook が読む | その行に書かれた名前だけを通す | AI 自身がその行を書けるので、歯止めとしては半分。hook がファイルを読むようになり、行の形を崩すと止まる |
| C. 決まりにない名前のときだけ確認画面を出す | `permissionDecision: ask` | 直すたびに確認が出る。「確認画面を出さない（うっかり承認を防ぐ）」という設計と逆になる |

**残した判定**: AI-DESK の外、ルート直下のファイル、保管フォルダの直下、`bin`・`out`・`.` で始まる名前などのフォルダ、
`00_TASK.md`、タスクフォルダの中のフォルダ（`材料\` と `NNB_…\` だけ。今回は変えないと利用者が決めた）、途中のリンク。

`$script:TaskFilePattern`・`$script:RoundFilePattern` は使われなくなったので消しました。
ルート直下のファイルを止めたときの文が「タスクフォルダそのものは、ファイルではありません」と分かりにくかったため、
「ルート直下にはファイルを置けません」と返すようにしました（`疎通確認` 8-4 で利用者の目に触れるため）。

### `疎通確認` 8-4 —— 試す先を変えた

1.4.0 までは「`00_疎通確認\メモ.md` が止まれば hook は正常」と試していました。1.5.0 では `メモ.md` が通ります。
試す先を**ルート直下の `点検メモ.md`** に変えました。`deny` に挙げていない場所なので、止まるとすれば hook の働きです。

### 残る穴 —— 正直に書いておきます

- **利用者がタスクフォルダに置いた資料（`00_TASK.md` 以外）は、hook では守られなくなりました。**
  1.2.0〜1.4.0 では、名前の決まりが、結果としてそれらも守っていました（`guard-write.ps1` の冒頭にもそう書いていた）。
  いまは「頼まれない限り書き換えない」という決まりだけです。README に「大事な原本は、タスクフォルダに置かないでください」と書きました
- **指定が無いのに AI が自由な名前で出しても、hook は止めません。** ただし 1.2.0 の事故の型
  （前の回のファイル名で出して上書き）は、もともと hook では防げていませんでした（番号の正しさは見ていない）。
  弱くなったのは「決まりにない名前」の歯止めだけです
- **確認ありのモードでの手数**: `settings.json` の `allow` には `議事録.md` のような名前が無いため、確認が出ることがあります。
  `settings.json` は人が設置したもので、変えていません（利用者の判断）
- **事故が多ければ見直す**ことを、利用者と約束しています。見直すときは、上の案 B が次の候補です

### どう確かめたか

- **hook の判定（36通り）**: `Get-WriteDecision` を直接呼ぶ試験。直下の `議事録.md`・`00_議事録.md`・`まとめ.xlsx`・

- **別プロセスとして（6通り）**: `new-instance.ps1` で仮のインスタンスを作り、標準入力の JSON と終了コードで同じ判定になること。
