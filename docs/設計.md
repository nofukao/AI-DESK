# AI-DESK 1.0.0 の設計 — なぜこの構造なのか

作成: 2026-09-14

この文書は、**将来の自分と、後から加わるメンバーのため**のものです。
「なぜこうなっているのか」が分からないと、良かれと思って壊してしまうためです。

**採用しなかった案も書いてあります。** そちらのほうが価値があることが多いからです。

---

## 1. インスタンスを git のクローンにしなかった

**インスタンスは、配布物フォルダの「コピー」です。`.git` は存在しません。**

クローンにすれば更新は `git pull` だけで済み、版ずれも起きません。**それでも採りませんでした。**

理由は1つです。**インスタンスの中には業務の機密情報が入ります。**
そこに `.git` があると、誰かが `git add .` と `git push` をした瞬間に外部へ出ます。
**push は実質的に取り消せません。** 履歴を書き換えても、既にクローンされていれば手遅れです。

事故の確率は低いかもしれません。しかし**起きたときの損害が回復不能**です。
更新の手間（`update-instance.ps1` を叩く）は、その保険料として安いと判断しました。

この判断は、配布物の `CLAUDE.md`「絶対遵守ルール2: Git の不使用」として利用者にも伝えています。
**理由まで書いてあります。** 理由の分からない禁止は、いつか誰かに破られるからです。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| インスタンスも clone にする | 上記。**この1点で却下** |
| clone にしたうえで `.gitignore` で業務データを除外 | 除外の設定を間違えた瞬間に出ます。**間違えたことに気づけない**のが致命的 |
| インスタンスをシンボリックリンク／ジャンクションで共有 | 1か所直すと全員に即座に効く反面、**壊したときも全員に効きます。** 段階的な更新ができません |

## 2. 配布物フォルダを `AI-DESK\` と名付けた

開発リポジトリの中に `AI-DESK\` があり、その中身は**完成品のインスタンスとまったく同じ形**です。
そのままコピーすれば動きます。「配布物 = インスタンスのひな形」を、形で示しています。

**副作用があります。見た目が完成品なので、開発中にうっかりそこで実際の仕事をしてしまいます。**

対策を2つ重ねました。

1. **`.gitignore` のホワイトリスト方式**（→ 7）。後から増えたものは追跡されません
2. **開発用 `CLAUDE.md` に明記**。「`AI-DESK\` の中で実際の業務を行わない」

### 採らなかった案

`dist\` や `template\` という名前にする案がありました。取り違えは起きにくくなります。
しかし**コピーしたあとのフォルダ名が変わってしまう**か、リネームの手順が1つ増えます。
「コピーすればそのまま動く」という分かりやすさを優先しました。

---

## 3. `CLAUDE.md` と `PROFILE.md` を分けた

旧構成では、規則も業務知識も 1 つの `CLAUDE.md`（約28KB）に入っていました。
これを2つに割りました。

| ファイル | 中身 | 配布 | 現場で直せるか |
|---|---|---|---|
| `CLAUDE.md` | どの組織でも通用する規則 | する | **直さない**（コピーなので消える） |
| `PROFILE.md` | その組織の前提知識（業態・用語・資料の場所） | しない | **自由** |

**理由は2つあります。**

1. **可搬性。** 業務知識が混ざったままでは、他の組織・他の部署にコピーできません
2. **リポジトリを Public にできる。** 実在の会社名・取引先名・物件名が配布物から消えました。
   この分離が済むまでは Public 化を検討できません

読み込みは `CLAUDE.md` の冒頭に置いた `@PROFILE.md` の 1 行で行われます。
`PROFILE.md` が無くても規則はすべて有効で、**「前提知識が無いから作業しない」とはさせません。**

1.0.0 では同じ考えで、**読み取り範囲を `.claude\settings.local.json`** に分けていました。
**1.1.0 で、読み取り範囲の設定そのものをやめました**（→ 14）。

## 4. インスタンスの識別を、フォルダ名ではなく `.ai-desk\VERSION` にした

**`.ai-desk\VERSION` があるフォルダが、インスタンスのルートです。**
フォルダ名は `AI-DESK` でも `AI-DESK1` でも `営業部AI-DESK` でもかまいません。

**理由は、名前を自由にし、何個でも置けるようにするためです。**

- 通常業務用と実験用を分けたい
- 部署ごとに置きたい
- NAS が使えないときだけローカルで作業したい

フォルダ名で判定すると、この全部ができなくなります。
また、**名前の規則は必ず破られます**（「AI-DESK_旧」「AI-DESK - コピー」）。
**ファイルの有無なら、破りようがありません。**

この判断は規則の根幹なので、`CLAUDE.md` の「【最重要】書く場所を間違えないために」の中で
定義してあります。

---

## 5. 規則の判定条件に、パス区切り文字を使わない

「パス文字列に `\out\` が含まれるか」ではなく、
「**そのタスクフォルダの `out` の中か**」と**構造**で書いています。

**これは移植のための配慮ではありません。いま効く堅牢性です。**

- 文字列判定では、**ルート直下の `out` も、別のタスクの `out` も通ってしまいます**
- 同じフォルダが、道具によって次のように見えます。**すべて Windows 上の話です**

```
PowerShell から:   Z:\AI-DESK\202610_見積比較\out
Git Bash から:     /z/AI-DESK/202610_見積比較/out
WSL から:          /mnt/z/AI-DESK/202610_見積比較/out
```

**本文の説明や例で `out\` と書くのは構いません**（読みやすさのため）。
直したのは「AI がこう判定せよ」と書いてある箇所だけです。

## 6. `Edit(*/out/**)` を変えずに済んだ

旧構成と新構成では、**カレントディレクトリから `out` までの深さが同じ**です。

```
旧: <個人フォルダ>\<タスク名>\out\     ← カレント = 個人フォルダ
新: <インスタンス>\<タスク名>\out\     ← カレント = インスタンスのルート
```

`.claude\settings.json` の `Edit(*/out/**)` は「カレントの1階層下の `out`」を意味します。
（1.0.0 では `Write(*/out/**)` も併記していましたが、**`Write(...)` のパス指定は一度も参照されていませんでした。** → 10）
**個人名の階層が消えたのに深さが変わらないため、権限設定に一切手を入れていません。**

これは偶然ではなく、**そうなるように新構成を決めました。**
権限設定は動作確認が難しく、間違えたときに気づきにくい部分です。触らずに済むなら、それが最善です。

なお `settings.json` のパターンは `Edit(*/out/**)` と `/` 区切りで書きます。
**この記法は全 OS 共通**で、元から中立でした。

## 7. `.gitignore` をホワイトリスト方式にした

```gitignore
/AI-DESK/**
!/AI-DESK/CLAUDE.md
!/AI-DESK/.claude/skills/**
    …
```

`AI-DESK\` の中をいったん全部無視し、**既知の配布物だけを `!` で戻しています。**

**理由**: `AI-DESK\` は見た目が完成品のインスタンスなので、
**開発中にうっかり実際のタスクフォルダを作ってしまう**ことが十分あり得ます。
ブラックリスト方式（`*.xlsx` を無視する等）では、想定していない形のものが漏れます。

**この方式の代償**: 配布物にファイルを足したら、`.gitignore` にも `!` 行を足す必要があります。
足し忘れると**追跡されません（＝ push されない）。安全側に倒れます。**
実際、フェーズ1で `settings.local.json.example` の `!` 行が漏れており、
`git check-ignore` で検出して足しました。**代償が想定どおりに働いた**形です。

## 8. 版ずれ問題と、配布原本による解き方

**新構成の最大の弱点です。**

旧構成の強みは「ルールの実体が1つしかない」ことでした。1か所直せば全員に効きます。
新構成では**インスタンスの数だけ `CLAUDE.md` のコピーが増え、必ず版がずれます。**
これは避けられません。**避けられないので、「ずれを見つけられる」ようにしました。**

```
<社内の配布原本>\AI-DESK\        ← 社内で1か所。publish.ps1 が置く
        .ai-desk\VERSION         ← 1.2.0

<任意の場所>\AI-DESK\            ← インスタンス
        .ai-desk\VERSION         ← 1.0.0
        .ai-desk\source.txt      ← 配布原本のパスが書いてある
```

1. `.ai-desk\VERSION` に版番号を持つ
2. `.ai-desk\source.txt` に**どこから来たか**を記録する（`new-instance.ps1` が書く）
3. **`疎通確認` が、配布元の版と自分の版を比べて知らせる** ← **これが一番効きます**
4. `update-instance.ps1` は、上書き前に差分を表示する
5. 現場での `CLAUDE.md` 直接編集は禁止。改訂案を `out\` に出して管理者に渡す導線がある

**「ルールの実体は1つ」という強みを、配布原本という形で取り戻しました。**
インスタンスは増えても、**原本は1つ**です。

配布元に届かない場合（NAS に繋がっていない、原本が移動した）は、
**失敗ではなく「確認できませんでした」と報告させます。** 嘘をつかせないためです。

### スキルは、利用者が自由に育ててよい

旧構成では、共通スキルを1か所に置けば全員に効きました。**新構成ではこれが失われます。**

**失われてよい**と判断しました。本システムは開発途上であり、
現状の仕様で利用者を縛るほうが、有用性を損なうリスクが大きいためです。
利用者は自分のインスタンスでスキルを追加・改造できます（AI がやる場合は承諾が要ります）。

代わりに2つ決めました。

- **配布物のスキル（`初期設定`・`疎通確認`・`継続タスク`）を直接書き換えると、次の更新で消える**（`CLAUDE.md` に明記）
- **利用者が足したスキルは、更新で触らない**（`update-instance.ps1` の仕様）

## 9. 配布物の一覧を、別に持たない

`new-instance.ps1` / `update-instance.ps1` / `publish.ps1` の3本は、
**「配布物フォルダの中に実在するファイル」を走査**します。マニフェストを別に持ちません。

**理由**: 一覧を二重に持つと、必ずずれます。
この作りなら「**配布物に無いものは触らない**」が、仕様ではなく**構造として**成り立ちます。
タスクフォルダも `PROFILE.md` も `settings.local.json` も、走査結果に現れないので触られません。

代償は、**開発リポジトリの `AI-DESK\` にゴミを置くと配布されてしまう**ことです。
`.gitignore`（→ 7）と、`publish.ps1` の確認表示で受け止めています。

## 10. 歯止めを「確認プロンプト」から「deny」へ移した（1.1.0）

> **この節の「例外3つ」と「読み取り範囲と `deny` の対」は、1.1.0 の公開前に取りやめ、
> hook に置き換えました（→ 14）。** 判断の経緯として残します。

**受け入れテストで穴が見つかりました。** 権限モードが「Auto」のとき、
ルート直下の `out\` への書き込みが**確認なしで通りました。**

`settings.json` の `disableBypassPermissionsMode: "disable"` が塞ぐのは
bypassPermissions だけで、**「自動」は塞いでいませんでした。**

### 何が問題だったか

歯止めを **`allow` と確認プロンプト**に置いていたことです。これは
**「利用者がモードを切り替えない」という前提**の上に立っていました。
その前提は、利用者の手元で簡単に崩れます。しかも**崩れたことに誰も気づきません。**

### どう直したか

**`deny` は権限モードに関係なく効きます。** そこで歯止めを `deny` に移し、
**そのうえで既定を「自動」にしました。**

| | 1.0.0 | 1.1.0 |
|---|---|---|
| 既定のモード | 確認あり（`default`） | **Auto**（契約の既定に任せる。設定ファイルでは指定しない） |
| 何が守っていたか | `allow` ＋ 確認プロンプト | **`deny`** |
| モードを変えられたら | **歯止めが消える** | **変わらない** |
| 作業の手間 | 毎回確認が出る | **止まらない** |

「確認を出して止める」のをやめ、「そもそも書けなくする」に変えたので、
**安全性を上げながら、同時に手間を減らせました。** 両立しないと思っていた2つです。

規則は「**配布物（更新で上書きされるもの）には書けない**」の1本にまとめました。
例外は `PROFILE.md`（自由）、`.claude\skills\`（承諾を得て）、
`settings.local.json` の `additionalDirectories`（同上）の3つです。
**育てる場所と、揃えておく場所を、`deny` の有無で表現しています。**

### 読み取り範囲と書き込み禁止を、対にした

> **読んでよい場所は、書いてはいけない場所でもある。**

`settings.local.json` には、読める場所（`additionalDirectories`）と、
そこへの書き込み禁止（`Edit` の `deny`）を**対で**書きます。
分けて考えさせないので、片方だけ足して片方を忘れる、が起きにくくなります。

これで、**Auto モードでも、AI が直接行う書き込みは資料フォルダに届きません。**
過去に実際に起きた事故（成果物を資料フォルダに直接出力した）は、**AI が直接書いた場合に限り**、機械的に塞がりました。
スクリプト経由の書き込みは塞がりません（→ 下の「それでも残る穴」）。

### 残る穴 — 正直に書いておきます

| 穴 | なぜ塞げないか |
|---|---|
| **インスタンスの外への書き込み**（デスクトップなど） | 事前に列挙できないためです。「自動」では確認なしで通ります。**ここは規則だけが頼り**です |
| **`deny` を書いたファイル自身を、AI が編集できる** | `settings.local.json` は AI が `additionalDirectories` を足せる必要があります。同じファイルの中に `deny` があるため、原理的には外せます |

2つ目は、**予防ではなく発見で受け止めています。** `疎通確認` が毎回
「読める場所すべてに、対になる `deny` があるか」を検査し、崩れていれば異常として報告します。

3つ目の穴（`.claude\settings.json` 側の `deny`）は、そのファイル自体を `deny` しているため、
**AI からは外せません。** 守りの中心はこちらに置いてあります。

### 1.1.0 の最初の実装にあった誤り（公式ドキュメントとの照合で判明）

実機テストの途中で Claude Code の公式ドキュメントと照合したところ、**設定の書き方に4つの誤り**がありました。
いずれも**エラーにならず、黙って効かない**種類の誤りです。

| # | 誤り | 実際の挙動 | 直し方 |
|---|---|---|---|
| 1 | `"defaultMode": "acceptEdits"` で Auto を既定にしたつもりだった | `acceptEdits` は画面の「Edit automatically」で、**Auto とは別のモード**。しかも `auto` は**プロジェクトの設定ファイルからは指定できず**、VS Code 拡張は**プロジェクトの設定を開始モードに使わない** | `defaultMode` を**書かない**。Pro・Max・Team 契約では、指定しなければ Auto で始まる |
| 2 | `Edit(./out/**)` でルート直下の `out` を塞いだつもりだった | `./out/**` は `out/**` と同じ扱いで、**deny では深さを問わず当たる。すべてのタスクの `out` が塞がれ、何も出力できなくなる** | 先頭を `/` にする（`Edit(/out/**)`）。プロジェクト設定では、起動したフォルダの直下だけに当たる |
| 3 | `Write(...)` と `Edit(...)` を対で書いていた | ファイルの権限は **`Edit(...)` だけで判定され、`Write(...)` のパス指定は参照されない**（起動時に警告が出る） | `Edit(...)` だけにする。`Edit` の deny は Write ツールの書き込みも止める |
| 4 | 資料フォルダを `Edit(Z:/**)` で塞いだつもりだった | Windows のパスは照合前に `/z/...` に直される。`Z:/**` は**起動フォルダからの相対パス**と解釈され、**Z: には一切当たらない** | `Edit(//z/**)` と書く（`//` がドライブの根、ドライブ文字は小文字） |

**2 は、実機テストで 8-1 を行えば「何も出力できない」として表に出たはずの誤りです。**
**4 は、テストでは表に出にくい誤りです。** 資料フォルダに書こうとしない限り、効いていないことに気づけません。
**設定の書き方は、実機テストだけでなく、ドキュメントとの照合でも確かめる**必要があります。

### それでも残る穴（ドキュメントで確認した事実）

- **Python などのスクリプトが自分で開くファイルには、`deny` は効きません。** `Edit` の deny が見張るのは、
  Claude Code 自身のファイル操作と、Bash が名前を挙げて扱うファイル（`cat` やリダイレクト先など）だけです。
  抽出スクリプトの書き出し先は、**規則（`CLAUDE.md`）と、Auto モードの安全チェックが頼り**です。
  OS のレベルで塞ぐサンドボックス機能は、ドキュメント上 macOS・Linux・WSL2 向けです
- **`.claude\` の中は Claude Code の保護パスです。** Auto モードでも書き込みは安全チェックに回されます。
  `初期設定` が `settings.local.json` やスキルを書くとき、確認が出ることがあります。
  歯止めとしてはむしろ好都合です（AI が自分の deny を黙って外しにくい）

## 11. `PROFILE.md` を、最初から置かないことにした（1.1.0）

1.0.0 の `new-instance.ps1` は、`PROFILE.example.md` を `PROFILE.md` にコピーしていました。
**これは間違いでした。**

`CLAUDE.md` の `@PROFILE.md` は、それを**毎回自動で読み込みます。** つまり作りたての
インスタンスでは、AI が**架空の会社（サンプル商事・事務機器の卸売）を、この組織の事実として
読み込んでいました。** `疎通確認` も「`PROFILE.md` はある → 正常」と報告していました。

**空である以上に悪い状態です。** 空なら「分からないので聞く」ですが、
これは「知っているつもりで間違える」です。

### どう直したか

**作らないことにしました。** 無ければ `@PROFILE.md` は何も読み込みません。

「マーカーを置いて、中身は無視しろと AI に指示する」方式も検討しましたが、採りませんでした。
**読んでから忘れろ、は読まないより弱い**ためです。

代わりに `初期設定` スキルを追加し、**対話で聞き取って作る**ようにしました。
手で書きたい人のために `PROFILE.example.md` は配り続け、
**手でコピーした人が中身を書き換え忘れた場合**に備えて、記入例には判別用の1行
（`AI-DESK-PROFILE-EXAMPLE`）を入れてあります。保険は残しつつ、主たる経路を変えた形です。

`settings.local.json` も同じ理由で作らないことにしました（その後、読み取り範囲の設定そのものをやめました → 14）。

### 「要らない」と言えること

前提知識を登録しない運用も選べます。その場合は `AI-DESK-PROFILE-NONE` を含む
`PROFILE.md` を書き、**以後は申し出ません。**
「いまはいい」（次回また聞く）と「要らない」（もう聞かない）を区別しています。
**一度断られたことを何度も聞くのは、それ自体が害**だからです。

## 12. マルチプラットフォーム対応は、当面やらない

### 決定

**AI-DESK は Windows 専用とします。** macOS / Linux 対応は行いません。

### 理由

1. **実際の利用がほぼ Windows**です
2. **動作確認のできない `.sh` を配るのは、無いよりかえって危険**です。
   「用意してある」と思って使われ、壊れていたときに誰も直せません

### それでも守った4点

「やらない」と「やれなくする」は違います。**いずれも追加コストがほぼゼロで、
後から施すと大仕事になるもの**だけを守りました。

| # | 守ったこと | なぜ今か |
|---|---|---|
| 1 | OS 依存の記述を `CLAUDE.md` の「実行環境について（Windows）」1章に集約 | 28KB の文書に後から施すのは大仕事。**分割のついでなら無料** |
| 2 | 規則の判定条件にパス区切り文字を使わない（→ 5） | **移植と無関係に、いま効く堅牢性** |
| 3 | `.gitattributes` に `*.sh text eol=lf` | 1行。将来 `.sh` を足したとき CRLF 混入で即死するのを防ぐ |
| 4 | `.ps1` でパスを文字列連結せず `Join-Path` を使う | 書き始めれば無料。PowerShell 7 は mac/Linux でも動くので、**移植の目が残る** |

### 今回の分割の副産物として、大半はすでに中立になっている

| 項目 | 状態 |
|---|---|
| ドライブレター | **解決済み** — 配布物に書かない。`PROFILE.md` と `task.md` に書く（サイト固有） |
| 業務フォルダのパス | **解決済み** — `PROFILE.md` へ |
| `settings.json` のパターン記法 | **元から中立** — `Edit(*/out/**)` と、全 OS で `/` 表記 |
| Office/PDF 抽出（openpyxl, pandas, pdfplumber…） | **元から中立** |
| タスクフォルダ方式・命名規則・作業記録 | **元から中立** |
| PowerShell スクリプト5本（hook を含む） | **残る依存その1** |
| `py` / cp932 / `.ps1` の BOM / 260文字制限 | **残る依存その2**（1章に集約済み） |

### 再開するときの手順

1. スクリプト3本と hook（`guard-write.ps1`）の `.sh` 版を書く（`setup_python.ps1` は winget 依存なので別途）
2. `CLAUDE.md` の「実行環境について（Windows）」に、macOS の節を足す
3. `py` → `python3` の分岐を入れる

**上の4点を守ってあれば、おおよそ1日**です。守っていなければ `CLAUDE.md` 全体の書き直しになります。

## 14. 読み取り範囲の設定をやめ、書き込み先を hook で限った（1.1.0）

**10 で作った「読み取り範囲と `deny` の対」を、公開前に取りやめました。**

### きっかけ

実機で `初期設定` を試したところ、読み取り範囲（`settings.local.json`）を最初に決めさせる流れに、
次の疑問が出ました。

- 読む場所は、**依頼（タスク）ごとに違う。** 最初に一度決めるより、`task.md` で指定するほうが自然
- **AI が読める範囲は、使っている人が読める範囲と同じ。** 設定を誤っても、AI が人以上の権限を持つことはない
- **本当に限りたいのは「書く場所」**で、それは「タスクフォルダ（特に `out`）だけ」と言い切れる

### deny では「ここだけ」と書けない

Claude Code の公式ドキュメントに、次のとおりあります。

> a deny rule can't carry allowlist exceptions

`deny` は「ここは禁止」を**並べる**方式で、「ここ以外は全部禁止」とは書けません。
だから 10 では、読める場所ごとにドライブの `deny` を対で書かせる必要があり、
**列挙できないデスクトップなどへの書き込みは、穴として残っていました。**

### hook なら「ここだけ」と書ける

`PreToolUse` の hook は、AI がファイルを書く直前に、決まったスクリプトを走らせる仕組みです。

> A hook that exits with code 2 stops the tool call before permission rules are evaluated

権限ルールより前に止めるので、**Auto を含むどのモードでも効きます。**
`.claude\hooks\guard-write.ps1` が書き込み先を調べ、次の3つ以外を止めます。

| 書いてよい場所 | 理由 |
|---|---|
| `<ルート>\<タスクフォルダ>\out\` の中 | 成果物の置き場所。AI-DESK の約束そのもの |
| `<ルート>\PROFILE.md` | `初期設定` と「PROFILE に足して」のため |
| `<ルート>\.claude\skills\` の中 | スキルを育てる自由度のため（→ 8） |

- タスクフォルダは「ルート直下のフォルダ。ただし `.` で始まるもの・`bin`・`task_template`・`out` を除く」
- **`out` だけ**にしました。`task.md` は人が書いた依頼なので、AI には書き換えさせません
- 判定は文字列の見た目でなく、**絶対パスに直してから構造で**行います（→ 5）。
  `/c/...` の形、`/` 区切り、相対パス、`..`、大文字小文字の違いを吸収します
- 途中にジャンクション・シンボリックリンクがあれば止めます（見た目は `out` の中でも、実体が資料フォルダになりうるため）
- **判定できない形のパスや、スクリプト内のエラーは、止める側に倒します**
- インスタンスのルートは、スクリプトの2つ上のフォルダ（`.ai-desk\VERSION` があること）で決めます。
  起動したフォルダの名前には頼りません（→ 4）

### 読む側は、設定しない

- Auto モードでは、AI-DESK の外も確認なしで読めます（最初の1回だけ「読み続けてよいか」の確認が出ます）
- 読む場所は `task.md` の「見てほしい資料の場所」「見なくてよい場所」に従わせます
- 読ませたくない場所は、`PROFILE.md` の「**AI に読ませない場所**」（任意）に書きます。
  **読むことは、中身を AI のサービスへ送ることでもある**ためです。これは規則であって、機械的な禁止ではありません
- 副次効果: `additionalDirectories` を使わなくなったので、Z: が「作業フォルダ扱い」でなくなり、
  Z: への編集が自動承認の対象から外れました

### 付随して決めたこと

| 決めたこと | 理由 |
|---|---|
| `autoMemoryEnabled: false` | 自動メモリは `%USERPROFILE%\.claude\projects\...\memory\` に書きます。**`out` の外への書き込み**なので hook に止められ、失敗を繰り返すだけになります。組織の知識の置き場所は `PROFILE.md` です |
| `disableAllHooks: false` を明記 | ユーザー設定で hook を全部止めていても、プロジェクト設定の `false` が優先されるため |
| `deny` に `settings.local.json` と `hooks\` を追加 | hook が動かなかったときの2枚目の壁。`settings.local.json` に `disableAllHooks: true` を書かれると hook が止まるため |
| `settings.local.json.example` を配布物から外した | 読み取り範囲の設定が要らなくなったため |

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| タスクごとに `settings.local.json` を書き換える | Auto モードでは、読むのに設定が要らない。AI が自分の権限設定を毎回書き換えるのは、歯止めの意味を弱める |
| `dontAsk` モード（許可したもの以外すべて拒否） | Python の実行やシェルのコマンドまで1つずつ許可が要り、作業にならない。モードの切り替えにも出てこず、起動時の指定が要る |
| サンドボックス（プログラムの書き込みまで OS で縛る） | 公式ドキュメント上、macOS・Linux・WSL2 のみ。**Windows ネイティブは非対応** |
| シェルのコマンド文字列を hook で検査する | 変数や Python の中の書き出し先は見えない。**止めているつもりになる**ほうが危ない |
| 共有フォルダを読み取り専用にした別の Windows アカウントで AI を動かす | **プログラムの書き込みまで塞げる唯一の方法。** ただし情報システム側の作業になるため、今は採らない |

### 残る穴 — 正直に書いておきます

| 穴 | 手当て |
|---|---|
| **PowerShell が起動できない・時間切れ**のとき、書き込みは止まらない（Claude Code の仕様） | `deny`（ルートの `out`・配布物・設定ファイル）を2枚目の壁として残した。`疎通確認` 8-4 で、hook が実際に止めるかを毎回試す |
| **信頼（「このフォルダを信頼しますか」）を断ると、hook は動かない** | 同上。README で「必ず承諾」と案内している |
| **プログラム（Python など）が書くファイル** | 規則（実行前に書き出し先を確かめる）と、フルパスでの報告 |
| hook の設定は、セッション中に書き換えると即座に反映される | AI が設定ファイルを直接書くことは hook と `deny` で止まる。プログラム経由の書き換えは `疎通確認` 8-1 で発見する |
| 書き込み1回ごとに PowerShell を起動する | 実測で1回 0.5 秒前後。許容範囲と判断 |

### どう確かめたか

- **単体試験（40通り）**: 仮インスタンスに対して判定だけを走らせた。`out` の中・`PROFILE.md`・スキルは通り、
  `task.md`・ルートの `out`・設定ファイル・別インスタンス・ジャンクション経由・`..` での脱出・代替データストリーム・
  UNC などはすべて止まった。200万文字の書き込み内容でも 0.6 秒前後
- **実機試験**: Claude Code 2.1.270 と 2.1.197 に配布物の `settings.json` を読ませ、`acceptEdits` モード
  （作業フォルダ内の編集が自動承認される）で書かせた。`out` の中は書け、`task.md`・`00_疎通確認` 直下・
  作業フォルダに加えた外部フォルダへの書き込みは、**hook のメッセージで止まり、ファイルは変わらなかった**
- **未確認**: 実際のインスタンスでの `疎通確認`（信頼ダイアログを通した状態）、プランモードとの相性

## 15. ネットワークドライブで、履歴の一覧が空になる問題（1.1.0）

### 症状と原因

AI-DESK をネットワークドライブ（`Z:` など）に置くと、VS Code の Claude Code で、履歴の一覧が空になります。
**Claude Code 側の不具合です。** 公開の不具合報告もあります（anthropics/claude-code の #31219・#33140・#63527 など）。

- Claude Code は履歴を `.claude\projects\<作業フォルダのパスの英数字以外を - にした名前>\` に保存する
- **保存する側は `Z:\...` のまま**名前を作る
- **VS Code 拡張は、一覧を探す前に実体のパス（`\\サーバー\共有\...`）に解決する**
- 名前が食い違い、探す先のフォルダが存在しないので、一覧が空になる

旧構成でも同じことが起きており、そのときは PC ごとに手でジャンクションを作って直していました。

### どう直したか

`bin\setup_history.ps1` を配布物に入れました。「一覧が探す名前」で「実際の保存先」を指す
ジャンクションを1本作ります。**PC ごと・インスタンスごとに1回**必要です。

**そのうえで、セッション開始時の hook（`SessionStart`）で、毎回 `-Quiet` で自動実行します。**
履歴は PC ごとに保存されるので、その PC で最初のセッションを始めた時点で入口ができます。
**履歴が溜まる前に直るため、利用者は症状に出会いません。**

- 移動・削除・上書きをしない。既に別のリンクや本物のフォルダがあれば、何もしない
- `-Quiet` は何も表示せず、常に終了コード 0 で終わる。
  `SessionStart` の標準出力は AI の文脈に入り、0 以外の終了コードは利用者にエラー表示が出るため
- 対象は `startup` と `resume`。`/clear` や圧縮のたびには走らせない
- 自動で直らなかったとき（信頼していない、hook が止められている など）は、`疎通確認` の 10 が見つける。
  AI が手で実行するときは**ユーザーの承諾を得てから**（`setup_python.ps1` と同じ扱い）
- Claude Code 側で直っても、ジャンクションは同じフォルダを指すだけなので無害

**利用者に聞かずにユーザーのフォルダへ書き込む**ことになりますが、書くのはジャンクション1本だけで、
管理者（配布物）の判断として採りました。AI が自分の判断で書き込むのとは区別しています。

### AI-DESK 以外でも使えるようにした

同じ症状は、AI-DESK に限らず、ネットワークドライブ上のフォルダで Claude Code を使えば起きます。
そこで `setup_history.ps1` を**単体でも使える形**にしました。

- 既定の対象は「いまの作業フォルダ」。AI-DESK の中に置かなくても動く
- ファイルの先頭に **AI 向けの手順**（調べる → 承諾を得て直す → 開き直しを案内する）を書いた。
  利用者は、このファイルを添付するかフォルダに置いて「これを実行して」と頼むだけでよい
- `-All` で、この PC の履歴にあるネットワークドライブ上のフォルダをまとめて直せる。
  フォルダ名からは元のパスを戻せないため、履歴ファイルに記録された作業フォルダを読み、
  そこから作った名前がフォルダ名と一致するものだけを対象にする

**形態として、スキルは採りませんでした。** スキルは PC ごと・プロジェクトごとに置く手間があり、
「困ったときに1回渡す」使い方に合わないためです。
AI が手順書（Markdown）を読んで毎回コマンドを書き起こす方式も、結果がぶれるため採りませんでした。
**決まった処理はスクリプトに、判断と説明は AI に**、という分担です。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| `CLAUDE_CODE_PROJECT_DIR_NAME` で保存先の名前を固定する | `CLAUDE_CONFIG_DIR` も必要で、**起動前に環境変数で設定しなければならない**（設定ファイルの `env` では効かない）。利用者に起動のしかたを変えさせることになる |
| `\\サーバー\共有\...` で直接開いてもらう | コマンドプロンプトなど、UNC を作業フォルダにできない道具がある。`PROFILE.md` や過去の記録も `Z:\` の書き方 |
| AI-DESK をローカルに置くよう求める | 共有フォルダに置けることは、AI-DESK の利点の1つ（→ 4） |
| `new-instance.ps1` で自動で行う | 作った人の PC にしか効かない。使う PC ごとに要る |
| AI が承諾を得て手で実行するだけにする | 症状に気づいてからでないと直らない。気づかないまま「履歴が消えた」と思われる |

### あわせて直したこと — hook の、パスの書き方の違い

同じ系統の不具合報告に、**デスクトップ版の Claude Code が `Z:` を `\\サーバー\共有\...` に解決する**ものがあります（#44152）。
書き込み制限の hook は、インスタンスのルートと書き込み先を比べるため、
**片方が `Z:\...`、もう片方が `\\サーバー\共有\...` だと、`out` への書き込みまで止めてしまいます。**
止める側に倒れるので危険ではありませんが、何も出力できなくなります。

そこで、**2つの書き方が混ざったときだけ、両方を `\\サーバー\共有\...` に揃えてから比べる**ようにしました。
揃えるのは、ドライブの割り当て（`Get-PSDrive` の `DisplayRoot`）から分かる範囲だけです。

### どう確かめたか

- `setup_history.ps1`: 作業用の仮の置き場で17通り（調べるだけ・作成・再実行・既存の履歴が見えるか・
  本物のフォルダがある場合・別のリンクがある場合・ローカルの場合・存在しないフォルダ・
  `-Quiet` で何も表示せず 0 で終わるか・既定の対象が作業フォルダか・`-All` が一致するフォルダだけを直すか）
- hook: 実際のドライブの割り当てを使い、`Z:\...` と `\\サーバー\共有\...` を混ぜた10通りの判定。既存の40通りも再実行
- `SessionStart`: Claude Code 2.1.270 で、配布物と同じ呼び方（`${CLAUDE_PROJECT_DIR}` と `-Quiet`）のまま、
  対象と履歴の置き場だけを試験用に差し替えて起動した。**セッション開始時にジャンクションができ、
  エラー表示も AI への余計な出力も無かった**
- 実機: 利用者の PC で、Z: 上のテスト用インスタンスの履歴が、一覧に出るようになった（手で作ったジャンクションによる）
- **未確認**: 新しい PC で、自動実行だけで一覧に出ること
