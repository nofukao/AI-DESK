# AI-DESK 1.0.0 の設計 — なぜこの構造なのか

作成: 2026-09-14

この文書は、**将来の自分と、後から加わるメンバーのため**のものです。
「なぜこうなっているのか」が分からないと、良かれと思って壊してしまうためです。

**採用しなかった案も書いてあります。** そちらのほうが価値があることが多いからです。

---

## 1. インスタンスを git のクローンにしなかった

**インスタンスは、配布物フォルダの「コピー」です。`.git` は存在しません。**

クローンにすれば更新は `git pull` だけで済み、版ずれも起きません。**それでも採りませんでした。**

理由は1つです。**インスタンスの中には業務の機密情報が入ります。**
そこに `.git` があると、誰かが `git add .` と `git push` をした瞬間に外部へ出ます。
**push は実質的に取り消せません。** 履歴を書き換えても、既にクローンされていれば手遅れです。

事故の確率は低いかもしれません。しかし**起きたときの損害が回復不能**です。
更新の手間（`update-instance.ps1` を叩く）は、その保険料として安いと判断しました。

この判断は、配布物の `CLAUDE.md`「絶対遵守ルール2: Git の不使用」として利用者にも伝えています。
**理由まで書いてあります。** 理由の分からない禁止は、いつか誰かに破られるからです。

### 採らなかった案

| 案 | なぜ採らなかったか |
|---|---|
| インスタンスも clone にする | 上記。**この1点で却下** |
| clone にしたうえで `.gitignore` で業務データを除外 | 除外の設定を間違えた瞬間に出ます。**間違えたことに気づけない**のが致命的 |
| インスタンスをシンボリックリンク／ジャンクションで共有 | 1か所直すと全員に即座に効く反面、**壊したときも全員に効きます。** 段階的な更新ができません |

## 2. 配布物フォルダを `AI-DESK\` と名付けた

開発リポジトリの中に `AI-DESK\` があり、その中身は**完成品のインスタンスとまったく同じ形**です。
そのままコピーすれば動きます。「配布物 = インスタンスのひな形」を、形で示しています。

**副作用があります。見た目が完成品なので、開発中にうっかりそこで実際の仕事をしてしまいます。**

対策を2つ重ねました。

1. **`.gitignore` のホワイトリスト方式**（→ 7）。後から増えたものは追跡されません
2. **開発用 `CLAUDE.md` に明記**。「`AI-DESK\` の中で実際の業務を行わない」

### 採らなかった案

`dist\` や `template\` という名前にする案がありました。取り違えは起きにくくなります。
しかし**コピーしたあとのフォルダ名が変わってしまう**か、リネームの手順が1つ増えます。
「コピーすればそのまま動く」という分かりやすさを優先しました。

---

## 3. `CLAUDE.md` と `PROFILE.md` を分けた

旧構成では、規則も業務知識も 1 つの `CLAUDE.md`（約28KB）に入っていました。
これを2つに割りました。

| ファイル | 中身 | 配布 | 現場で直せるか |
|---|---|---|---|
| `CLAUDE.md` | どの組織でも通用する規則 | する | **直さない**（コピーなので消える） |
| `PROFILE.md` | その組織の前提知識（業態・用語・資料の場所） | しない | **自由** |

**理由は2つあります。**

1. **可搬性。** 業務知識が混ざったままでは、他の組織・他の部署にコピーできません
2. **リポジトリを Public にできる。** 実在の会社名・取引先名・物件名が配布物から消えました。
   この分離が済むまでは Public 化を検討できません

読み込みは `CLAUDE.md` の冒頭に置いた `@PROFILE.md` の 1 行で行われます。
`PROFILE.md` が無くても規則はすべて有効で、**「前提知識が無いから作業しない」とはさせません。**

同じ考えで、**読み取り範囲は `.claude\settings.local.json`** に分けました。
これも配布しません。「どこに何があるか」を教えるのが `PROFILE.md`、
「どこを読んでよいか」を機械的に決めるのが `settings.local.json` です。**役割が違います。**

## 4. インスタンスの識別を、フォルダ名ではなく `.ai-desk\VERSION` にした

**`.ai-desk\VERSION` があるフォルダが、インスタンスのルートです。**
フォルダ名は `AI-DESK` でも `AI-DESK1` でも `営業部AI-DESK` でもかまいません。

**理由は、名前を自由にし、何個でも置けるようにするためです。**

- 通常業務用と実験用を分けたい
- 部署ごとに置きたい
- NAS が使えないときだけローカルで作業したい

フォルダ名で判定すると、この全部ができなくなります。
また、**名前の規則は必ず破られます**（「AI-DESK_旧」「AI-DESK - コピー」）。
**ファイルの有無なら、破りようがありません。**

この判断は規則の根幹なので、`CLAUDE.md` の「【最重要】書く場所を間違えないために」の中で
定義してあります。

---

## 5. 規則の判定条件に、パス区切り文字を使わない

「パス文字列に `\out\` が含まれるか」ではなく、
「**そのタスクフォルダの `out` の中か**」と**構造**で書いています。

**これは移植のための配慮ではありません。いま効く堅牢性です。**

- 文字列判定では、**ルート直下の `out` も、別のタスクの `out` も通ってしまいます**
- 同じフォルダが、道具によって次のように見えます。**すべて Windows 上の話です**

```
PowerShell から:   Z:\AI-DESK\202610_見積比較\out
Git Bash から:     /z/AI-DESK/202610_見積比較/out
WSL から:          /mnt/z/AI-DESK/202610_見積比較/out
```

**本文の説明や例で `out\` と書くのは構いません**（読みやすさのため）。
直したのは「AI がこう判定せよ」と書いてある箇所だけです。

---

## 6. `Write(*/out/**)` を変えずに済んだ

旧構成と新構成では、**カレントディレクトリから `out` までの深さが同じ**です。

```
旧: <個人フォルダ>\<タスク名>\out\     ← カレント = 個人フォルダ
新: <インスタンス>\<タスク名>\out\     ← カレント = インスタンスのルート
```

`.claude\settings.json` の `Write(*/out/**)` は「カレントの1階層下の `out`」を意味します。
**個人名の階層が消えたのに深さが変わらないため、権限設定に一切手を入れていません。**

これは偶然ではなく、**そうなるように新構成を決めました。**
権限設定は動作確認が難しく、間違えたときに気づきにくい部分です。触らずに済むなら、それが最善です。

なお `settings.json` のパターンは `Write(*/out/**)` と `/` 区切りで書きます。
**この記法は全 OS 共通**で、元から中立でした。

## 7. `.gitignore` をホワイトリスト方式にした

```gitignore
/AI-DESK/**
!/AI-DESK/CLAUDE.md
!/AI-DESK/.claude/skills/**
    …
```

`AI-DESK\` の中をいったん全部無視し、**既知の配布物だけを `!` で戻しています。**

**理由**: `AI-DESK\` は見た目が完成品のインスタンスなので、
**開発中にうっかり実際のタスクフォルダを作ってしまう**ことが十分あり得ます。
ブラックリスト方式（`*.xlsx` を無視する等）では、想定していない形のものが漏れます。

**この方式の代償**: 配布物にファイルを足したら、`.gitignore` にも `!` 行を足す必要があります。
足し忘れると**追跡されません（＝ push されない）。安全側に倒れます。**
実際、フェーズ1で `settings.local.json.example` の `!` 行が漏れており、
`git check-ignore` で検出して足しました。**代償が想定どおりに働いた**形です。

## 8. 版ずれ問題と、配布原本による解き方

**新構成の最大の弱点です。**

旧構成の強みは「ルールの実体が1つしかない」ことでした。1か所直せば全員に効きます。
新構成では**インスタンスの数だけ `CLAUDE.md` のコピーが増え、必ず版がずれます。**
これは避けられません。**避けられないので、「ずれを見つけられる」ようにしました。**

```
<社内の配布原本>\AI-DESK\        ← 社内で1か所。publish.ps1 が置く
        .ai-desk\VERSION         ← 1.2.0

<任意の場所>\AI-DESK\            ← インスタンス
        .ai-desk\VERSION         ← 1.0.0
        .ai-desk\source.txt      ← 配布原本のパスが書いてある
```

1. `.ai-desk\VERSION` に版番号を持つ
2. `.ai-desk\source.txt` に**どこから来たか**を記録する（`new-instance.ps1` が書く）
3. **`疎通確認` が、配布元の版と自分の版を比べて知らせる** ← **これが一番効きます**
4. `update-instance.ps1` は、上書き前に差分を表示する
5. 現場での `CLAUDE.md` 直接編集は禁止。改訂案を `out\` に出して管理者に渡す導線がある

**「ルールの実体は1つ」という強みを、配布原本という形で取り戻しました。**
インスタンスは増えても、**原本は1つ**です。

配布元に届かない場合（NAS に繋がっていない、原本が移動した）は、
**失敗ではなく「確認できませんでした」と報告させます。** 嘘をつかせないためです。

### スキルは、利用者が自由に育ててよい

旧構成では、共通スキルを1か所に置けば全員に効きました。**新構成ではこれが失われます。**

**失われてよい**と判断しました。本システムは開発途上であり、
現状の仕様で利用者を縛るほうが、有用性を損なうリスクが大きいためです。
利用者は自分のインスタンスでスキルを追加・改造できます（AI がやる場合は承諾が要ります）。

代わりに2つ決めました。

- **配布物の2スキルを直接書き換えると、次の更新で消える**（`CLAUDE.md` に明記）
- **利用者が足したスキルは、更新で触らない**（`update-instance.ps1` の仕様）

## 9. 配布物の一覧を、別に持たない

`new-instance.ps1` / `update-instance.ps1` / `publish.ps1` の3本は、
**「配布物フォルダの中に実在するファイル」を走査**します。マニフェストを別に持ちません。

**理由**: 一覧を二重に持つと、必ずずれます。
この作りなら「**配布物に無いものは触らない**」が、仕様ではなく**構造として**成り立ちます。
タスクフォルダも `PROFILE.md` も `settings.local.json` も、走査結果に現れないので触られません。

代償は、**開発リポジトリの `AI-DESK\` にゴミを置くと配布されてしまう**ことです。
`.gitignore`（→ 7）と、`publish.ps1` の確認表示で受け止めています。

## 10. 歯止めを「確認プロンプト」から「deny」へ移した（1.1.0）

**受け入れテストで穴が見つかりました。** 権限モードが「自動（acceptEdits）」のとき、
ルート直下の `out\` への書き込みが**確認なしで通りました。**

`settings.json` の `disableBypassPermissionsMode: "disable"` が塞ぐのは
bypassPermissions だけで、**「自動」は塞いでいませんでした。**

### 何が問題だったか

歯止めを **`allow` と確認プロンプト**に置いていたことです。これは
**「利用者がモードを切り替えない」という前提**の上に立っていました。
その前提は、利用者の手元で簡単に崩れます。しかも**崩れたことに誰も気づきません。**

### どう直したか

**`deny` は権限モードに関係なく効きます。** そこで歯止めを `deny` に移し、
**そのうえで既定を「自動」にしました。**

| | 1.0.0 | 1.1.0 |
|---|---|---|
| 既定のモード | 確認あり（`default`） | **自動（`acceptEdits`）** |
| 何が守っていたか | `allow` ＋ 確認プロンプト | **`deny`** |
| モードを変えられたら | **歯止めが消える** | **変わらない** |
| 作業の手間 | 毎回確認が出る | **止まらない** |

「確認を出して止める」のをやめ、「そもそも書けなくする」に変えたので、
**安全性を上げながら、同時に手間を減らせました。** 両立しないと思っていた2つです。

規則は「**配布物（更新で上書きされるもの）には書けない**」の1本にまとめました。
例外は `PROFILE.md`（自由）、`.claude\skills\`（承諾を得て）、
`settings.local.json` の `additionalDirectories`（同上）の3つです。
**育てる場所と、揃えておく場所を、`deny` の有無で表現しています。**

### 読み取り範囲と書き込み禁止を、対にした

> **読んでよい場所は、書いてはいけない場所でもある。**

`settings.local.json` には、読める場所（`additionalDirectories`）と、
そこへの書き込み禁止（`Write` / `Edit` の `deny`）を**対で**書きます。
分けて考えさせないので、片方だけ足して片方を忘れる、が起きにくくなります。

これで、**「自動」モードでも資料フォルダには一切書けません。**
過去に実際に起きた事故（成果物を資料フォルダに直接出力した）は、機械的に塞がりました。

### 残る穴 — 正直に書いておきます

| 穴 | なぜ塞げないか |
|---|---|
| **インスタンスの外への書き込み**（デスクトップなど） | 事前に列挙できないためです。「自動」では確認なしで通ります。**ここは規則だけが頼り**です |
| **`deny` を書いたファイル自身を、AI が編集できる** | `settings.local.json` は AI が `additionalDirectories` を足せる必要があります。同じファイルの中に `deny` があるため、原理的には外せます |

2つ目は、**予防ではなく発見で受け止めています。** `疎通確認` が毎回
「読める場所すべてに、対になる `deny` があるか」を検査し、崩れていれば異常として報告します。

3つ目の穴（`.claude\settings.json` 側の `deny`）は、そのファイル自体を `deny` しているため、
**AI からは外せません。** 守りの中心はこちらに置いてあります。

## 11. `PROFILE.md` を、最初から置かないことにした（1.1.0）

1.0.0 の `new-instance.ps1` は、`PROFILE.example.md` を `PROFILE.md` にコピーしていました。
**これは間違いでした。**

`CLAUDE.md` の `@PROFILE.md` は、それを**毎回自動で読み込みます。** つまり作りたての
インスタンスでは、AI が**架空の会社（サンプル商事・事務機器の卸売）を、この組織の事実として
読み込んでいました。** `疎通確認` も「`PROFILE.md` はある → 正常」と報告していました。

**空である以上に悪い状態です。** 空なら「分からないので聞く」ですが、
これは「知っているつもりで間違える」です。

### どう直したか

**作らないことにしました。** 無ければ `@PROFILE.md` は何も読み込みません。

「マーカーを置いて、中身は無視しろと AI に指示する」方式も検討しましたが、採りませんでした。
**読んでから忘れろ、は読まないより弱い**ためです。

代わりに `初期設定` スキルを追加し、**対話で聞き取って作る**ようにしました。
手で書きたい人のために `PROFILE.example.md` は配り続け、
**手でコピーした人が中身を書き換え忘れた場合**に備えて、記入例には判別用の1行
（`AI-DESK-PROFILE-EXAMPLE`）を入れてあります。保険は残しつつ、主たる経路を変えた形です。

`settings.local.json` も同じ理由で作りません。架空のパスが書かれたファイルが置かれると、
`疎通確認` が存在しないフォルダを読もうとして失敗します。

### 「要らない」と言えること

前提知識を登録しない運用も選べます。その場合は `AI-DESK-PROFILE-NONE` を含む
`PROFILE.md` を書き、**以後は申し出ません。**
「いまはいい」（次回また聞く）と「要らない」（もう聞かない）を区別しています。
**一度断られたことを何度も聞くのは、それ自体が害**だからです。

## 12. マルチプラットフォーム対応は、当面やらない

### 決定

**AI-DESK は Windows 専用とします。** macOS / Linux 対応は行いません。

### 理由

1. **実際の利用がほぼ Windows**です
2. **動作確認のできない `.sh` を配るのは、無いよりかえって危険**です。
   「用意してある」と思って使われ、壊れていたときに誰も直せません

### それでも守った4点

「やらない」と「やれなくする」は違います。**いずれも追加コストがほぼゼロで、
後から施すと大仕事になるもの**だけを守りました。

| # | 守ったこと | なぜ今か |
|---|---|---|
| 1 | OS 依存の記述を `CLAUDE.md` の「実行環境について（Windows）」1章に集約 | 28KB の文書に後から施すのは大仕事。**分割のついでなら無料** |
| 2 | 規則の判定条件にパス区切り文字を使わない（→ 5） | **移植と無関係に、いま効く堅牢性** |
| 3 | `.gitattributes` に `*.sh text eol=lf` | 1行。将来 `.sh` を足したとき CRLF 混入で即死するのを防ぐ |
| 4 | `.ps1` でパスを文字列連結せず `Join-Path` を使う | 書き始めれば無料。PowerShell 7 は mac/Linux でも動くので、**移植の目が残る** |

### 今回の分割の副産物として、大半はすでに中立になっている

| 項目 | 状態 |
|---|---|
| ドライブレター | **解決済み** — `settings.local.json` へ（サイト固有） |
| 業務フォルダのパス | **解決済み** — `PROFILE.md` へ |
| `settings.json` のパターン記法 | **元から中立** — `Write(*/out/**)` と、全 OS で `/` 表記 |
| Office/PDF 抽出（openpyxl, pandas, pdfplumber…） | **元から中立** |
| タスクフォルダ方式・命名規則・作業記録 | **元から中立** |
| PowerShell スクリプト4本 | **残る依存その1** |
| `py` / cp932 / `.ps1` の BOM / 260文字制限 | **残る依存その2**（1章に集約済み） |

### 再開するときの手順

1. スクリプト3本の `.sh` 版を書く（`setup_python.ps1` は winget 依存なので別途）
2. `CLAUDE.md` の「実行環境について（Windows）」に、macOS の節を足す
3. `py` → `python3` の分岐を入れる

**上の4点を守ってあれば、おおよそ1日**です。守っていなければ `CLAUDE.md` 全体の書き直しになります。

## 13. この構成で解決したこと / 解決しないこと

| 解決したこと | どうやって |
|---|---|
| 置き場所が `Z:` に固定されていた | フォルダごとコピーできる形にした |
| 個人名の階層が構造に埋め込まれていた | `<インスタンス>\<タスク名>\out\` にした |
| Antigravity が上位階層の `CLAUDE.md` を読めず、回りくどく案内していた | 規則がカレントディレクトリ直下に来たので、`type CLAUDE.md` で済む |
| 業務知識と規則が同じファイルに混ざっていた | `PROFILE.md` に分けた |
| メンバー追加のたびに個人フォルダテンプレートをコピーしていた | `new-instance.ps1` |
| 前提知識の記入が、人の手作業だった | `初期設定` スキルが対話で作る（1.1.0） |
| 権限モードを切り替えると歯止めが消えた | 歯止めを `deny` に移した（1.1.0） |

| 解決しないこと | なぜ |
|---|---|
